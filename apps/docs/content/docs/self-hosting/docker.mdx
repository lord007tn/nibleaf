Nibleaf ships with Docker Compose files for local development, production-style
self-hosting, and Coolify. The standard self-host stack starts only the product
services: dashboard/docs app, API, worker, and datastores. The Coolify production
stack also exposes the internal admin panel on a separate operator domain.

## Services

| Service | Port | Purpose |
| --- | --- | --- |
| `app` | `4310` | Dashboard, editor, live docs routes, and the `/api` proxy |
| `server` | `4311` | Hono API, auth, project data, publishing endpoints |
| `worker` | `4312` | BullMQ workers for publishing, search, email, and analytics |
| `postgres` | `5442 -> 5432` | Primary database for Prisma |
| `dragonfly` | `6379` | Redis-compatible queue backend |
| `maxio` | `9300 -> 9000` | S3-compatible object storage for uploads |

## Coolify stack

Use `docker-compose.coolify.yml` in Coolify for production.

Bind these Coolify domains to services:

| Host binding | Service | Port | Purpose |
| --- | --- | --- | --- |
| `app.example.com` | `app` | `4310` | Dashboard, editor, and `/api` proxy |
| `admin.example.com` | `admin` | `4315` | Internal platform admin panel |
| `*.docs.example.com` | `app` | `4310` | Free project subdomains |
| `cname.docs.example.com` | `app` | `4310` | Custom-domain CNAME target |
| `storage.example.com` | `maxio` | `9000` | Optional public media/storage origin |

Set `SITE_BASE_DOMAIN` to your wildcard docs domain, for example
`docs.example.com`, then bind `*.docs.example.com` to the `app` service in
Coolify.
Set `CUSTOM_DOMAIN_CNAME_TARGET` to the host customers should CNAME to, for
example `cname.docs.example.com`, then bind that host to the same `app` service.

Coolify generates the service URL, user, password, and hex secret variables used
by the compose file. Assign domains first, then set only the product-specific
values manually.

The Coolify stack defaults app containers to
`ghcr.io/lord007tn/nibleaf:latest`. Set `NIBLEAF_IMAGE` only when you want to pin a
specific release tag or digest.

```dotenv
SITE_BASE_DOMAIN=docs.example.com
CUSTOM_DOMAIN_CNAME_TARGET=cname.docs.example.com
```

The compose file consumes these generated Coolify variables:

| Variable | Source |
| --- | --- |
| `SERVICE_URL_APP` | Dashboard/app domain assigned to `app:4310`. |
| `SERVICE_URL_ADMIN` | Admin domain assigned to `admin:4315`. |
| `SERVICE_URL_MAXIO` | Storage/media domain assigned to `maxio:9000`. |
| `SERVICE_USER_POSTGRES` | Generated Postgres username. |
| `SERVICE_PASSWORD_64_POSTGRES` | Generated Postgres password. |
| `SERVICE_USER_STORAGE` | Generated maxio/S3 access key. |
| `SERVICE_PASSWORD_64_STORAGE` | Generated maxio/S3 secret key. |
| `SERVICE_HEX_64_NIBLEAF` | Generated auth secret. |

The Coolify stack defaults to bundled maxio storage. To use Cloudflare R2, AWS
S3, Backblaze B2, or another S3-compatible store, set `STORAGE_PROVIDER`,
`STORAGE_ENDPOINT`, `STORAGE_REGION`, `STORAGE_BUCKET`,
`STORAGE_FORCE_PATH_STYLE`, `STORAGE_ACCESS_KEY_ID`,
`STORAGE_SECRET_ACCESS_KEY`, `STORAGE_PUBLIC_ENDPOINT`, and
`STORAGE_PUBLIC_URL` to that external bucket. Keep `STORAGE_PUBLIC_ENDPOINT`
browser-reachable because presigned upload/download URLs use it.
The app/server/worker containers do not wait on local maxio health, so external
object-storage deployments can leave the bundled storage service unused.

Create these DNS records before verifying domains in Nibleaf:

| Name | Type | Value |
| --- | --- | --- |
| `app.example.com` | `CNAME`, `A`, or `AAAA` | Coolify app ingress |
| `admin.example.com` | `CNAME`, `A`, or `AAAA` | Coolify admin ingress |
| `*.docs.example.com` | `CNAME`, `A`, or `AAAA` | Coolify app ingress |
| `cname.docs.example.com` | `CNAME`, `A`, or `AAAA` | Coolify app ingress |

For Cloudflare, use DNS-only mode first if certificate issuance or host
verification fails, then enable proxying after Coolify has certificates for the
dashboard, wildcard docs host, and custom-domain CNAME target.

Customer custom domains need their own DNS records:

| Name | Type | Value |
| --- | --- | --- |
| `docs.customer.com` | `CNAME` | `cname.docs.example.com` |
| `_nibleaf.docs.customer.com` | `TXT` | `nibleaf-verify=<token shown in Nibleaf>` |

For apex custom domains such as `customer.com`, use Cloudflare CNAME flattening
or an `A`/`AAAA` record to the same app ingress, plus the `_nibleaf.customer.com`
TXT verification record.

## Local development stack

Use the dev compose file when you want infrastructure only and plan to run the
Node services with `pnpm dev`.

```bash
cp .env.example .env
docker compose -f docker-compose.dev.yml up -d
pnpm db:deploy
pnpm db:seed
pnpm dev
```

Open the dashboard at [http://localhost:4310](http://localhost:4310). The seed
creates `demo@nibleaf.test` with password `nibleafdemo123`.

## Production-style stack

Use the main compose file when you want containers for every service.

```bash
cp .env.example .env
openssl rand -hex 32
# Put the generated value in BETTER_AUTH_SECRET.
docker compose up -d --build
```

Create the first account at
[http://localhost:4310/sign-up](http://localhost:4310/sign-up). Production mode
does not create demo credentials unless you explicitly enable seeding.

## Verify the deployment

```bash
docker compose ps
curl http://localhost:4311/health
curl http://localhost:4312/health
```

Then publish a small docs change from the dashboard and open the live site from
the project overview.

For subdomain/custom-domain verification, also check:

```bash
curl -H "Host: <project>.docs.example.com" https://<coolify-app-host>/
curl -H "Host: docs.customer.com" https://<coolify-app-host>/
```

The first request should serve the project whose deployment name is `<project>`.
The second request serves a project only after the custom domain is added and
verified in Nibleaf.

## Persistence

Postgres, Dragonfly, and maxio use Docker volumes. Do not run
`docker compose down -v` unless you intend to delete the database, queue state,
and stored assets.

<Callout type="warning">
  For production, do not publish datastore ports to the public internet. Keep
  Postgres, Dragonfly, and maxio on the internal Docker network and expose only
  your reverse proxy.
</Callout>
