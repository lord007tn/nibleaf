Nibleaf is configured through environment variables. Start by copying the example
file and then replace every demo secret before production use.

```bash
cp .env.example .env
```

## Required production values

| Variable | Purpose |
| --- | --- |
| `NODE_ENV` | Set to `production` for production deployments. |
| `BETTER_AUTH_SECRET` | Strong random secret used to sign auth state. |
| `POSTGRES_PASSWORD` | Password for the bundled Postgres user. |
| `STORAGE_ACCESS_KEY` | Access key for bundled maxio object storage. |
| `STORAGE_SECRET_KEY` | Secret key for bundled maxio object storage. |
| `BETTER_AUTH_URL` | Browser-facing dashboard origin, for example `https://app.example.com`. |
| `TRUSTED_ORIGINS` | Comma-separated origins allowed by Better Auth. |
| `CORS_ALLOWED_ORIGINS` | Comma-separated origins allowed by the API. |
| `PUBLIC_APP_URL` | Public dashboard origin. |
| `PUBLIC_API_URL` | Public API origin. In standard Compose, this is the dashboard origin because `/api` is proxied by `app`. |
| `PUBLIC_STORAGE_ENDPOINT` / `STORAGE_PUBLIC_ENDPOINT` | Browser-reachable S3 endpoint used for presigned upload/download URLs. Standard Compose reads the `PUBLIC_*` alias; Coolify/raw S3 env uses `STORAGE_PUBLIC_ENDPOINT`. |
| `PUBLIC_STORAGE_URL` | Public base URL for uploaded assets. |
| `SITE_BASE_DOMAIN` | Wildcard docs base for free project subdomains, for example `docs.example.com`. |
| `CUSTOM_DOMAIN_CNAME_TARGET` | Host customers CNAME custom domains to, for example `cname.docs.example.com`. |

Generate secrets with OpenSSL:

```bash
openssl rand -hex 32      # BETTER_AUTH_SECRET
openssl rand -base64 24   # POSTGRES_PASSWORD
openssl rand -base64 24   # STORAGE_SECRET_KEY
```

<Callout type="warn">
  The production entrypoint refuses to boot with an empty or known demo
  `BETTER_AUTH_SECRET`.
</Callout>

## Database

Nibleaf uses PostgreSQL through Prisma.

```dotenv
POSTGRES_URL=postgresql://nibleaf:<password>@postgres:5432/nibleaf
```

For local development outside Docker, `.env.example` points at the dev compose
port:

```dotenv
POSTGRES_URL=postgresql://nibleaf:nibleaf@localhost:5442/nibleaf
```

Run migrations manually with:

```bash
pnpm db:deploy
```

## Queues

Background work uses BullMQ on Dragonfly, a Redis-compatible server.

| Variable | Purpose |
| --- | --- |
| `REDIS_HOST` | Dragonfly/Redis hostname. |
| `REDIS_PORT` | Dragonfly/Redis port. |
| `REDIS_PASSWORD` | Optional password. |
| `REDIS_DB` | Database index. |
| `QUEUE_CLUSTER` | Hash-tag BullMQ queue names so Dragonfly can group queue keys. Defaults to `true`. |
| `WORKER_QUEUES` | Optional comma-separated queue allowlist. |
| `PUBLISH_CONCURRENCY` | Concurrent publish jobs. |
| `SEARCH_CONCURRENCY` | Concurrent search indexing jobs. |
| `EMAIL_CONCURRENCY` | Concurrent email jobs. |
| `ANALYTICS_CONCURRENCY` | Concurrent analytics jobs. |

The bundled Dragonfly containers run with `--cluster_mode=emulated` and
`--lock_on_hashtags`. Keep `QUEUE_CLUSTER=true` unless you are intentionally
pointing Nibleaf at a Redis-compatible backend that should not use hash-tagged
queue names.

## Object storage

The bundled stack uses maxio for S3-compatible local object storage. You can keep
maxio or point Nibleaf at Cloudflare R2, AWS S3, Backblaze B2, or another
S3-compatible service.

```dotenv
STORAGE_PROVIDER=maxio
STORAGE_ENDPOINT=http://maxio:9000
STORAGE_PUBLIC_ENDPOINT=https://storage.example.com
STORAGE_REGION=auto
STORAGE_BUCKET=nibleaf
STORAGE_ACCESS_KEY_ID=<access-key>
STORAGE_SECRET_ACCESS_KEY=<secret-key>
STORAGE_FORCE_PATH_STYLE=true
STORAGE_PUBLIC_URL=https://cdn.example.com/nibleaf
```

`STORAGE_ENDPOINT` is the server-side S3 endpoint. `STORAGE_PUBLIC_ENDPOINT`
must be reachable by the browser because presigned upload/download URLs use it.
`STORAGE_PUBLIC_URL` is the public asset/CDN base used in rendered docs.

Use `STORAGE_FORCE_PATH_STYLE=true` for maxio and R2. AWS S3 usually uses
virtual-hosted style and can set it to `false`.

## Authentication and origins

`BETTER_AUTH_URL` should be the dashboard origin that the browser uses. In the
standard Compose topology, the dashboard also proxies API calls under `/api`, so
cookies remain first-party.

```dotenv
BETTER_AUTH_URL=https://app.example.com
TRUSTED_ORIGINS=https://app.example.com,https://example.com
CORS_ALLOWED_ORIGINS=https://app.example.com,https://example.com
PUBLIC_APP_URL=https://app.example.com
PUBLIC_API_URL=https://app.example.com
```

## Docs domains

Nibleaf serves published docs from the dashboard app service. Two domain concepts
need to be configured:

- Free project subdomains: `<deployment-name>.<SITE_BASE_DOMAIN>`.
- Customer custom domains: a verified hostname such as `docs.customer.com`.

```dotenv
SITE_BASE_DOMAIN=docs.example.com
CUSTOM_DOMAIN_CNAME_TARGET=cname.docs.example.com
```

In DNS, point both the wildcard docs base and the CNAME target at the same app
ingress:

| Record | Type | Target |
| --- | --- | --- |
| `*.docs.example.com` | `CNAME`, `A`, or `AAAA` | Coolify app ingress |
| `cname.docs.example.com` | `CNAME`, `A`, or `AAAA` | Coolify app ingress |

In Cloudflare, keep those records on the same proxy mode as the dashboard app
record. If Cloudflare proxies the records, configure Coolify to accept the host
headers and issue certificates for the wildcard/docs hosts. Nibleaf only resolves
the incoming `Host`; TLS termination and wildcard certificates are handled by
Cloudflare, Coolify, or your reverse proxy.

### Coolify variable names

`docker-compose.coolify.yml` follows the same generated-variable pattern used by
the working Keenpix deploy. Coolify supplies service URLs, generated users,
generated passwords, and generated hex secrets:

| Coolify variable | Purpose |
| --- | --- |
| `SERVICE_URL_APP` | Public dashboard/app URL used for auth, CORS, and frontend build args. |
| `SERVICE_URL_ADMIN` | Public admin panel URL, for example `https://admin.example.com`. |
| `SERVICE_URL_MAXIO` | Public bundled-storage URL used for browser uploads and asset URLs. |
| `SERVICE_USER_POSTGRES` | Postgres username. |
| `SERVICE_PASSWORD_64_POSTGRES` | Postgres password. |
| `SERVICE_USER_STORAGE` | maxio access key. |
| `SERVICE_PASSWORD_64_STORAGE` | maxio secret key. |
| `SERVICE_HEX_64_NIBLEAF` | Better Auth signing secret. |

Set `SITE_BASE_DOMAIN` and `CUSTOM_DOMAIN_CNAME_TARGET` manually in the Coolify
environment screen. Assign the admin service to its own restricted operator
domain, for example `admin.example.com`.

Bundled maxio remains the default in Coolify. For external object storage, set
`STORAGE_PROVIDER`, `STORAGE_ENDPOINT`, `STORAGE_REGION`, `STORAGE_BUCKET`,
`STORAGE_FORCE_PATH_STYLE`, `STORAGE_ACCESS_KEY_ID`,
`STORAGE_SECRET_ACCESS_KEY`, `STORAGE_PUBLIC_ENDPOINT`, and
`STORAGE_PUBLIC_URL` values to your R2/S3-compatible bucket. Those explicit
storage values override the generated maxio variables.

The app containers do not depend on local `maxio` health at startup. Bucket
creation and CORS setup are best-effort on API boot, so external object-storage
deployments can start without waiting for bundled storage.

## Email

Postmark is the preferred production sender. SMTP remains a fallback for
non-Postmark providers. Without either provider, Nibleaf still runs, but invites,
reset-password emails, and verification emails will only be logged/queued.

| Variable | Purpose |
| --- | --- |
| `EMAIL_FROM` | Default sender address. |
| `POSTMARK_API_KEY` | Postmark server token used by the worker SDK. |
| `POSTMARK_MESSAGE_STREAM` | Optional Postmark message stream. |
| `SMTP_URL` | SMTP fallback connection string for non-Postmark providers. |
| `REQUIRE_EMAIL_VERIFICATION` | Require users to verify email before sign-in. |

## Frontend build variables

Variables prefixed with `VITE_` are baked into the dashboard at build time.
Rebuild the image after changing them.

| Variable | Purpose |
| --- | --- |
| `VITE_API_URL` | API URL used by the built client. Standard Compose uses `http://server:4311`. |
| `VITE_APP_URL` | Dashboard URL. |
| `VITE_WWW_URL` | Marketing site URL. |
| `VITE_GITHUB_URL` | Repository link shown in the UI. |
