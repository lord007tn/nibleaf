ابدأ بملف `.env.production.example` المطابق للإصدار. يصف هذا المرجع المصدر الحالي؛
أما ملف Compose المثبّت للإصدار v0.2.0 وصورته فلهما حدود إصدار مستقلة. لا تحفظ
ملف `.env` المملوء بالأسرار في المستودع.

تستخدم الجداول الأولى قيم Compose الإنتاجية ما لم يُذكر خلاف ذلك. أما جداول
البحث والتحليلات والاتصالات والسجلات أدناه فتعرض **القيم الافتراضية للمخطط**.
تُعامل القيمة الفارغة كأنها غير مضبوطة. يعني «اختياري» أن قراءة البيئة لا تتطلب
المتغيّر، لكن الميزة قد تحتاج إليه. لا تصل قيمة `.env` إلى الحاوية إلا إذا مرّرها
Compose عبر `environment` أو `env_file`. اقرأ ملاحظات تمرير الإعدادات في نهاية المرجع.

## الصورة والتطبيق العام

| المتغيّر | مطلوب | القيمة الافتراضية | الغرض |
| --- | --- | --- | --- |
| `NIBLEAF_VERSION` | نعم عمليًا | `v0.2.0` في القالب الحالي | وسم إصدار GHCR. ثبّت إصدارًا موجودًا، وتجنب الوسوم المتحركة. يرفض سير عمل Docker اليدوي استبدال أي وسم إصدار `v*` موجود، فتكون وسوم الإصدارات المنشورة ثابتة وفق سياسة المستودع. |
| `APP_URL` | نعم | لا توجد | لوحة التحكم التي يتعامل معها المتصفح، ومصدر المصادقة المعتاد، من دون شرطة مائلة في النهاية. |
| `ADMIN_URL` | فقط عند إتاحة الإدارة | `http://localhost:4315` | المصدر العام لوحدة تحكم المشغّل الاختيارية. |
| `NIBLEAF_BIND` | لا | `127.0.0.1` | واجهة المضيف لمنفذ التطبيق. أبقِها على loopback عندما يكون الوكيل محليًا. |
| `APP_PORT` | لا | `4310` | منفذ المضيف المرتبط بحاوية التطبيق. |
| `BETTER_AUTH_URL` | لا | `APP_URL` | تجاوز صريح لأساس المصادقة. |
| `TRUSTED_ORIGINS` | لا | `APP_URL` | مصادر المصادقة مفصولة بفواصل. أدرج `APP_URL` و`ADMIN_URL` معًا عند إتاحة وحدة تحكم المشغّل حتى يبدأ انتحال الدعم الأصلي منها. |
| `CORS_ALLOWED_ORIGINS` | لا | `APP_URL` | مصادر واجهة API مفصولة بفواصل. أدرج `APP_URL` و`ADMIN_URL` معًا عندما تتصل وحدة تحكم المشغّل بواجهة API المشتركة مباشرة. |
| `PINO_LOG_LEVEL` | لا | `info` في الإنتاج | أدنى مستوى للسجلات المنظمة. |
| `PINO_LOG_FILE` | لا | فارغ | إعداد توافق قديم في المصدر الحالي: يحدد المجلد الأب لكتابة سجلات evlog، ولا يُحفظ اسم الملف المطلوب. استخدم `EVLOG_FS_DIR` واربط المجلد للاحتفاظ بالسجلات. |

### مصادقة Google OAuth

أنشئ عميل OAuth من نوع **تطبيق ويب** في Google Cloud، ثم اضبط ما يلي:

- مصدر JavaScript المسموح: قيمة `APP_URL` نفسها، مثل `https://nibleaf.example.com`.
- عنوان إعادة التوجيه المسموح: `${APP_URL}/api/auth/callback/google`.
- `GOOGLE_CLIENT_ID` و`GOOGLE_CLIENT_SECRET`: بيانات اعتماد العميل المطابقة.

يجب أن يكون المتغيّران موجودين وغير فارغين بعد إزالة المسافات المحيطة. يخفي Nibleaf زر Google عند غياب أي منهما حتى لا يدخل القارئ في مسار تسجيل دخول غير مكتمل. أعد تشغيل التطبيق بعد تغيير هذه القيم على الخادم.

| `MARKETING_GTM_ID` | لا | فارغة | معرّف حاوية GTM المفضّل لصفحات التسويق العامة. يظهر كبيانات عامة ولا يُحمّل إلا بعد موافقة الزائر الصريحة. اضبط وسم GA4 داخل GTM مع تعطيل مشاهدات الصفحة التلقائية؛ يرسل Nibleaf حدث `page_view` يدويًا لكل مسار مقبول والأحداث المدرجة في قائمة السماح. لهذا المتغيّر أولوية على `MARKETING_GA4_ID`. |

| `RATE_LIMIT_PUBLIC_PER_MIN` | لا | `300` | عدد طلبات تقديم الموقع العام لكل عنوان في الدقيقة. |
| `TRUSTED_PROXY_HOPS` | لا | `0` | عدد العناوين التي تلي عنوان العميل في `X-Forwarded-For`، بما فيها العناوين الخاصة. اضبط القيمة نفسها على التطبيق وواجهة API؛ راجع [طريقة حسابها](/ar/self-hosting/troubleshooting#يرى-القرّاء-رسالة-طلبات-كثيرة-جدًا). |

### عقد حاوية GTM

عند تفعيل `MARKETING_GTM_ID`، اضبط وسم Google واحدًا داخل GTM مع تعطيل مشاهدات الصفحة التلقائية ومشغّل تهيئة الصفحة المعتاد. ثم اضبط وسم حدث GA4 واحدًا يعمل عند الحدث المخصّص `nibleaf_marketing_event`، واجعل اسم حدث GA يُقرأ من متغيّر طبقة البيانات `event_name`. يستخدم Nibleaf هذا الغلاف الثابت للأسماء المدرجة في قائمة السماح: `page_view` و`sign_up` و`cta_clicked` و`free_tool_started` و`free_tool_completed` و`free_tool_cta_clicked`، لذلك لا تحتاج إلى ستة وسوم أحداث منفصلة داخل GTM. اربط متغيّرات الأحداث الآمنة الموثّقة فقط. لا تضف متغيّرات تقرأ حقول النماذج أو بيانات الحساب أو محتوى المستند أو قيم DOM عشوائية إلى التحليلات. أبقِ فحوص الموافقة مفعّلة على الوسمين. لا يحمّل Nibleaf الحاوية إلا بعد القبول، ويدفع `page_view` يدويًا واحدًا للمسار المقبول ولكل تنقّل لاحق داخل التطبيق، ويتوقف عن إرسال الأحداث عند سحب الموافقة.

### Model Context Protocol

| المتغيّر | مطلوب | القيمة الافتراضية | الغرض |
| --- | --- | --- | --- |
| `MCP_ENABLED` | لا | `false` | يفعّل نقطة `/api/mcp` المصادَق عليها والمرتبطة بالمشروع. أبقها معطّلة حتى تنجح فحوص الوكيل ودورة حياة المفتاح. |
| `MCP_ALLOWED_HOSTS` | لا | فارغة | أسماء مضيفين عامة إضافية مفصولة بفواصل. مضيفا `API_URL` و`APP_URL` مسموحان مسبقًا. تُرفض البروتوكولات والمسارات وحروف البدل وسلاسل التمرير الملتبسة. |
| `MCP_RATE_LIMIT_PER_MIN` | لا | `120` | طلبات MCP لكل مفتاح بجميع أنواعها التي تقبلها عملية API واحدة في الدقيقة. تُحفظ العدادات في ذاكرة كل عملية؛ لذا أضف حدًا عند بوابة الدخول أو الحافة المشتركة للتطبيق الشامل. |

| `MCP_PUBLISH_RATE_LIMIT_PER_HOUR` | لا | `6` | محاولات `publish_changes` لكل مفتاح التي تقبلها عملية API واحدة في الساعة. ولا تُحتسب إلا المحاولات التي تجتاز فحص رمز المعاينة. |

راجع [إعداد عميل MCP وتشغيله بأمان](/ar/self-hosting/mcp) قبل تفعيل نقطة النهاية.
مفاتيح API شخصية: ينشئ كل عضو مفتاحه، ويستطيع المسؤول إلغاء أي مفتاح لكن المالك
وحده يستطيع تدويره، وتظهر الأسرار مرة واحدة. ويجب ألا تُحفظ في أمثلة البيئة أو إعدادات المستودع.

## التحقق من تمرير الإعدادات في الإصدار

لا يتضمن ملف `docker-compose.prod.yml` المثبّت للإصدار v0.2.0 خدمة ClickHouse
أو Qdrant. ولا يمرّر متغيّرات التحليلات والبحث أو `AI_DRAFT_MODEL` أو
`MCP_WRITE_RATE_LIMIT_PER_MIN` أو `MCP_PUBLISH_RATE_LIMIT_PER_HOUR` أو
`WORKER_QUEUES` أو إعدادات التصدير أو إعدادات `EVLOG_*` الجديدة. وجود القيم في
`.env.production.example` لا يثبت وصولها إلى الخدمة. كما يحتاج الإعداد الجديد
إلى صورة تنفّذه؛ لا تضيف متغيّرات البيئة ميزة إلى صورة أقدم.

لنشر مبني على المصدر الحالي بعد مراجعته، ضع القيم الناقصة في ملف تجاوز مستقل.
مثلاً يمرّر `docker-compose.operator.yml` التالي حدّي MCP وقائمة سماح للعامل
تشمل كل الطوابير الحالية:

```yaml
services:
  server:
    environment:
      MCP_WRITE_RATE_LIMIT_PER_MIN: ${MCP_WRITE_RATE_LIMIT_PER_MIN:-20}
      MCP_PUBLISH_RATE_LIMIT_PER_HOUR: ${MCP_PUBLISH_RATE_LIMIT_PER_HOUR:-6}
  worker:
    environment:
      WORKER_QUEUES: ${WORKER_QUEUES:-publish,search,email,analytics,export,git,erasure}
```

أدرج الملف في كل عملية لاحقة:

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.operator.yml config --services
docker compose -f docker-compose.prod.yml -f docker-compose.operator.yml up -d
```

في مجلد التثبيت الموجّه، استخدم `docker-compose.yml` ملفاً أول. أدرج ملفات تجاوز
البحث والتحليلات أيضاً في الأمر نفسه. لا تنشر الإعداد النهائي الكامل لأنه يتضمن أسراراً.

يضيف `docker-compose.search.yml` خدمة Qdrant ومجموعة من متغيّرات البحث والمحادثة
إلى API والعامل. ضبط `QDRANT_API_KEY` للعميل وحده لا يفعّل مصادقة خدمة Qdrant؛
اضبط مفتاح الخادم أيضاً قبل إتاحته خارج الشبكة الخاصة. لا يمرّر الملف
`SEARCH_CHAT_SUGGESTIONS_TIMEOUT_MS` وبعض إعدادات البحث المتقدمة؛ أضف تعيينات
بيئة صريحة عند تغييرها. كما يختلف حد الرموز 60000 عن قيمة المخطط أعلاه.

يتضمن ملف التشغيل السريع من المصدر (`docker-compose.yml`) وملف Coolify خدمة
ClickHouse وقرص النسخ الاحتياطي وملف التعريف `analytics-tools`. تستخدم التهيئة
`CLICKHOUSE_USERNAME` و`CLICKHOUSE_PASSWORD` (البديل في التشغيل السريع
`nibleaf` و`nibleaf`)، أو `SERVICE_PASSWORD_64_CLICKHOUSE` المطلوب في Coolify.
تنشئ هذه بيانات اعتماد الخدمة؛ أما التطبيق فيستخدم متغيّرات القارئ والكاتب.
لا تستخدم بيانات التشغيل السريع في نشر عام.

يستخدم Coolify أيضاً `NIBLEAF_IMAGE_TAG` (البديل `latest`) و`SERVICE_USER_POSTGRES`
و`SERVICE_PASSWORD_64_POSTGRES` و`POSTGRES_DB` (البديل `nibleaf`) و
`SERVICE_HEX_64_NIBLEAF` وبدائل التخزين `SERVICE_USER_STORAGE` و
`SERVICE_PASSWORD_64_STORAGE`. ثبّت وسم صورة صريحاً واحتفظ بالأسرار المنشأة.
هذه مدخلات Compose وليست متغيّرات مخطط التطبيق. راجع الملف قبل نقل `.env` محمول إليه.

بعد إعادة إنشاء الخدمات، تحقق من الصحة والرفع والنشر والبحث وكل ميزة فعّلتها.
لا يثبت نجاح قراءة البيئة أو نقطة الصحة وصول البريد أو رصيد مزوّد الذكاء الاصطناعي
أو جودة الفهرس أو إمكانية استعادة النسخة الاحتياطية.
