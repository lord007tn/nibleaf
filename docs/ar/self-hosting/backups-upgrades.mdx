تتضمن مجموعة الاستعادة القابلة للاستخدام Postgres وتخزين الكائنات من النافذة
التشغيلية نفسها. وتُعد نسخة قاعدة البيانات من دون الأصول المرفوعة غير مكتملة.
احتفظ بنسخ خارج المضيف والحساب المستخدمين للخدمة الحية، وأثبت نجاح الاستعادة
قبل الاعتماد عليها.

نفّذ أوامر هذه الصفحة من مجلد عملية النشر. يحتوي المجلد الذي أنشأه برنامج التثبيت
الموجّه على `docker-compose.yml` و`.env` فقط، لذا يعثر `docker compose` على ملفه
مباشرة. أما في نسخة محلية من المستودع، فنفّذ أولًا
`export COMPOSE_FILE=docker-compose.prod.yml`، لأن `docker-compose.yml` هناك هو
منظومة البناء من المصدر.

## إنشاء نسخة احتياطية

خصّص نافذة صيانة: توقف الأوامر كتّاب التطبيق وmaxio حتى اكتمال النسختين. أوقف
أي كاتب خارجي أيضاً واستخدم `.env` واسم مشروع Compose الحاليين. يخرج الغلاف عند
أول فشل وتبقى الخدمات متوقفة للتحقيق. لا تنفّذ الإجراء مع عمليات رفع أو نشر أخرى.

أنشئ تفريغًا لـPostgres بالتنسيق المخصّص، ثم أرشف وحدة تخزين maxio المضمّنة:

```bash
set -eu
mkdir -m 700 -p backups
STAMP=$(date +%Y%m%d-%H%M%S)
docker compose --profile admin stop app admin server worker
docker compose stop maxio
docker compose exec -T postgres pg_dump -U nibleaf -d nibleaf --format=custom > "backups/nibleaf-db-$STAMP.dump"
MAXIO_VOLUME=$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}' "$(docker compose ps --all -q maxio)")
test -n "$MAXIO_VOLUME"
docker volume inspect "$MAXIO_VOLUME" >/dev/null
docker run --rm -v "$MAXIO_VOLUME":/data:ro -v "$PWD/backups":/backup alpine:3.22 tar czf "/backup/nibleaf-storage-$STAMP.tar.gz" -C /data .
cp -p .env "backups/env-$STAMP"
cp -p "${COMPOSE_FILE:-docker-compose.yml}" "backups/compose-$STAMP.yml"
ls -lh "backups/nibleaf-db-$STAMP.dump" "backups/nibleaf-storage-$STAMP.tar.gz"
docker compose up -d
```

تحدد هذه الأوامر وحدة التخزين المثبتة عند `/data` في حاوية maxio القائمة، لذا تعمل مع
أي اسم لمشروع Compose وتتوقف إذا تعذّر تحديدها. لا توجد حاويات R2 أو S3
الخارجية في هذه الوحدة، لذا تخطَّ هذه الأسطر واستخدم إمكانات المزوّد لإدارة
الإصدارات أو النسخ المتماثل، أو أنشئ نسخة احتياطية مستقلة للحاوية.

في مستودع المصدر، يكتشف `bash scripts/backup.sh` خادم مشروع Compose المحدّد
ووحدة maxio، بما في ذلك الحاويات المتوقفة، ويرفض غياب التخزين المضمّن ويكتب بيانًا للاستعادة. اضبط
`BACKUP_STORAGE=external` صراحةً لنسخ قاعدة البيانات وحدها وانسخ الحاوية الخارجية
بشكل منفصل. يمثّل `STORAGE_VOLUME` تأكيدًا اختياريًا للمسار المكتشف ولا يحدّد اسمًا
افتراضيًا للوحدة. لا يوقف السكربت الكتّاب ولا ينسخ `.env`؛ نفّذ ذلك بشكل منفصل.
افتراضي `COMPOSE_FILE` هو `docker-compose.prod.yml` و`BACKUP_DIR` هو `./backups`
و`RETENTION_DAYS` هو `14` و`PGUSER` و`PGDATABASE` هما `nibleaf`. يقبل ملف Compose
واحدًا؛ مع ملفات التجاوز استخدم غلافًا مراجعًا بقائمة ملفات النشر نفسها. ليس السكربت
من ملفات الإصدار المنشور.

يحتوي `.env` على الأسرار التي تجعل الاستعادة قابلة للاستخدام، ومنها مفاتيح تشفير
بيانات اعتماد Git والتكاملات. احتفظ بنسخة محمية منه بتحكم وصول مستقل. فمن دون هذه
المفاتيح لا يمكن فك تشفير بيانات الاعتماد المخزنة.

انقل الملفين إلى خارج المضيف باستخدام بيانات اعتماد منفصلة، وسجّل المعرّفات
والأحجام والطوابع الزمنية وسياسة الاحتفاظ وإصدار التطبيق.

## اختبار الاستعادة

لا تستبدل بيئة الإنتاج مطلقًا عند إجراء تمرين. أنشئ قاعدة بيانات ووجهة تخزين
ومصدر تطبيق معزولة، ثم استعد النسخة فيها. على مضيف منفصل يملك منظومته الخاصة،
وباستخدام قيمة `$STAMP` نفسها:

اضبط `STAMP` على اللاحقة المشتركة لملفات النسخة. ابدأ بقاعدة جديدة فارغة ووحدة
تخزين معزولة فارغة، ولا تشغّل خدمة الترحيل قبل الاستعادة. يرفض الفحص قاعدة بها
جداول عامة. لا توجّه الأوامر إلى مشروع Compose الحي؛ عند الفشل أبقِ خدمات التطبيق متوقفة.

استخدم مراجعة التطبيق التي أنشأت النسخة الاحتياطية. احتفظ بقاعدة البيانات ووحدة
التخزين السابقتين ولا تربطهما بتجربة الاستعادة. أبقِ خدمات التطبيق متوقفة حتى التحقق
من المخطط والسجلات المستعادة. عند الفشل احتفظ بالهدف والسجلات للتشخيص.

```bash
set -eu
docker compose --profile admin stop app admin server worker
# Resolve the target before starting maxio: a retained volume is never safe.
RESTORE_STORAGE_VOLUME=$(docker compose config --format json | python3 -c 'import json,sys; c=json.load(sys.stdin); v=next(v["source"] for v in c["services"]["maxio"]["volumes"] if v["target"]=="/data"); print(c["volumes"][v]["name"])')
test -n "$RESTORE_STORAGE_VOLUME"
if docker volume inspect "$RESTORE_STORAGE_VOLUME" >/dev/null 2>&1; then
  echo 'Refusing an existing storage volume; use a fresh isolated target' >&2
  exit 1
fi
docker compose up -d postgres dragonfly
test "$(docker compose exec -T postgres psql -U nibleaf -d nibleaf -Atc "SELECT count(*) FROM pg_tables WHERE schemaname='public'")" = 0
docker compose exec -T postgres pg_restore -U nibleaf -d nibleaf --exit-on-error < "backups/nibleaf-db-$STAMP.dump"
docker volume create "$RESTORE_STORAGE_VOLUME" >/dev/null
docker run --rm -v "$RESTORE_STORAGE_VOLUME":/data -v "$PWD/backups":/backup alpine:3.22 sh -ec 'test -z "$(ls -A /data)"; tar xzf "/backup/$1" -C /data' sh "nibleaf-storage-$STAMP.tar.gz"
```

بعد التحقق من المخطط وسجل الترحيلات والسجلات المستعادة، شغّل مراجعة التطبيق
المتوافقة فقط باستخدام `docker compose up -d`.

ثم تحقق من المشاريع والعضويات وأشجار الصفحات والمسودات الحالية وعمليات النشر ذات
الحالة `READY` والأصول المرفوعة وعزل المصادقة والبحث العام.

سجّل الزمن المنقضي وكل خطوة يدوية. لا يُعد رمز خروج ناجح لمهمة النسخ الاحتياطي
دليلًا على قابلية الاستعادة من دون نجاح استعادة معزولة.

## ترقية إصدار مثبّت

لا تُعد تشغيل برنامج التثبيت للترقية. فهو مخصص للتثبيتات الجديدة فقط، واستبدال
`.env` بأسرار مولّدة حديثًا يمنعك من الوصول إلى بياناتك الحالية.

**للانتقال من v0.1.2 إلى v0.2.1، اتبع [دليل الترقية](/ar/self-hosting/upgrade-v0-2).**
تتضمن تلك الترقية مرحلة وسيطة إلزامية. إذا غيّرت الإصدار وحده، فستُرفض الجدولة ولن يصبح
API وعامل المعالجة (worker) جاهزين.

في الترقيات الأخرى، اقرأ ملاحظات كل إصدار وسيط، وتحقق من أي تغييرات خاصة بالإصدار
في الترحيل أو التهيئة. أنشئ نسخة احتياطية واختبر استعادتها. ثم:

1. استبدل ملف Compose بالنسخة الموثّقة من الإصدار الهدف. أبقِ `.env` واسم مشروع
   Compose وأسماء وحدات التخزين. لا يشمل تغيير الإصدار وحده الإعدادات التي يمررها
   ملف Compose الجديد إلى الخدمات:

   ```bash
   VERSION=vX.Y.Z
   d=$(mktemp -d)
   curl -fsSLo "$d/docker-compose.yml" "https://github.com/lord007tn/nibleaf/releases/download/$VERSION/docker-compose.yml"
   curl -fsSLo "$d/SHA256SUMS" "https://github.com/lord007tn/nibleaf/releases/download/$VERSION/SHA256SUMS"
   (cd "$d" && grep '  docker-compose.yml$' SHA256SUMS | sha256sum -c -)
   cp "$d/docker-compose.yml" "${COMPOSE_FILE:-docker-compose.yml}"
   ```

2. اضبط `NIBLEAF_VERSION` في `.env` على وسم الإصدار الموجود نفسه:

   ```dotenv
   NIBLEAF_VERSION=vX.Y.Z
   ```

3. اسحب الخدمات وأعد إنشاءها:

   ```bash
   docker compose pull
   docker compose up -d
   ```

تحقق من ملخّص الصورة الرقمي، وسجل الترحيل، وسلامة الخدمات، وتسجيل الدخول،
وعملية رفع واحدة، وعملية نشر واحدة، وعملية بحث واحدة، وصفحة عامة واحدة.

## التراجع الآمن إلى الإصدار السابق

ترحيلات Prisma أحادية الاتجاه. إذا لم يُنفّذ أي ترحيل للمخطط، فثبّت الصورة السابقة،
واستعد ملف Compose السابق، وأعد إنشاء الخدمات. وإذا غيّر ترحيل قاعدة البيانات، فأوقف
عمليات الكتابة واستعد مجموعة الاستعادة السابقة للترقية قبل تشغيل التطبيق الأقدم. لا
تشغّل التطبيق الأقدم على المخطط المرحَّل.

يحتاج الرجوع من v0.2.1 إلى v0.1.2 أيضًا إلى التراجع عن الجداول الموضّح في
[دليل الترقية](/ar/self-hosting/upgrade-v0-2#التراجع-إلى-الإصدار-السابق). لا يكفي التراجع عن الجداول
وحده، ولا استعادة قاعدة البيانات وحدها.

لا تجمع ترقية التطبيق مع تغيير الإصدار الرئيسي لـPostgreSQL. تعامل مع ترقية
قاعدة البيانات على أنها مشروع مستقل للتفريغ والاستعادة.

## استعادة تحليلات ClickHouse

يعرّف ملفّا Compose للتشغيل السريع من المصدر ولـCoolify قرص `backups` عند `/var/lib/clickhouse/backups` على وحدة تخزين مسماة مستقلة.
يتضمن قالب الإنتاج للإصدار التالي القرص نفسه ضمن ملف التعريف الاختياري `analytics`.
لا يتضمن `docker-compose.prod.yml` في v0.2.1 خدمة ClickHouse أصلاً. جهّز خدمة مستقلة وتعيينات بيئة التطبيق أولاً. ثم اربط فيها وحدة تخزين عند `/var/lib/clickhouse/backups` وأضف الملف التالي بالمسار `/etc/clickhouse-server/config.d/backups.xml`:

```xml
<clickhouse>
  <storage_configuration><disks><backups><type>local</type><path>/var/lib/clickhouse/backups/</path></backups></disks></storage_configuration>
  <backups><allowed_disk>backups</allowed_disk></backups>
</clickhouse>
```
استخدم النسخ الأصلي المتوافق مع ClickHouse 25.8 بهوية مشغّل، دون كتابة كلمات المرور في سجل الأوامر.
نفّذ في عميل SQL موثّق:

```sql
BACKUP DATABASE nibleaf_analytics TO Disk('backups', 'analytics-20261106-001');
SELECT name, status, error FROM system.backups;
```

اختر اسماً فريداً، وتحقق من `BACKUP_CREATED`، ثم أرشف وحدة النسخ وشفّرها وانقلها خارج المضيف.
وجود نسخة على القرص الممتلئ نفسه لا يحمي من فقدانه. سجّل إصدار ClickHouse ومخطط القاعدة
والمستخدمين والأدوار وإصدار التطبيق وإعدادات الاحتفاظ وبصمات ملفات النسخة.
انسخ Postgres وتخزين الكائنات منفصلين؛ فهما غير مشمولين بنسخة التحليلات.

على خادم استعادة معزول بالإصدار نفسه وإعداد قرص النسخ نفسه، انسخ الملفات إلى القرص واستعدها في قاعدة جديدة:

```sql
RESTORE DATABASE nibleaf_analytics AS nibleaf_analytics_restore
FROM Disk('backups', 'analytics-20261106-001');
SELECT name, status, error FROM system.backups;
SELECT count(), uniqExact(event_id) FROM nibleaf_analytics_restore.analytics_events;
SELECT version FROM nibleaf_analytics_restore.analytics_schema_migrations FINAL ORDER BY version;
```

تحقق من `RESTORED`، وطابق الأعداد وعينات معرّفات الأحداث مع سجل النسخة.
اضبط `CLICKHOUSE_DATABASE=nibleaf_analytics_restore` و`POSTGRES_URL` معزولاً، ثم شغّل الترقيات
واختبر القراءات المقيدة بالمستأجر. أعد تطبيق عمليات محو المشاريع اللاحقة للنسخة قبل السماح بوصول التطبيق.
احتفظ بالمفاتيح والأملاح الحالية. لا تختبر الاستعادة فوق القاعدة التي تخدم المستخدمين.

يمكن للدالة `rebuildProjectAnalyticsRollups` إعادة بناء التجميعات من الأحداث الخام المتبقية.
لا يمكن إعادة تجميع فترات انتهى الاحتفاظ بأحداثها؛ وفقد الأحداث الخام يترك فجوات دائمة.
ينتهي الاحتفاظ بعبارات البحث الحساسة عمداً ولا يعاد إنشاؤها. لا تطبق افتراضات تجميع التحليلات على بيانات الفوترة والاستخدام.

قبل الترقية، ثبّت الصورة وأنشئ نسخة واختبر استعادتها وراجع توافق الإصدارات.
استعد إلى إصدار الخادم الأصلي أولاً ثم اتبع مسار الترقية المدعوم.
الترقيات التلقائية إضافية ولا تعيد المخطط إلى إصدار أقدم. تقصير الاحتفاظ لا يمكن التراجع عنه بعد الدمج.
هذه الأوامر إجراء تدريب على الاستعادة؛ ولا تعد دليلاً على نجاح استعادة نشرك إلا بعد تنفيذ استعادة معزولة ومطابقة البيانات.
يتبع إعداد القرص وأوامر SQL [مرجع النسخ الأصلي في ClickHouse](https://clickhouse.com/docs/operations/backup/disk).

إذا كنت تشغّل خدمة الإدارة عادة، فاستخدم `docker compose --profile admin up -d`
بدلاً من آخر `up -d` بعد نجاح النسخ أو الاستعادة. لا تعِد الكتّاب الخارجيين
إلا بعد التحقق. عند تعدد ملفات Compose، احتفظ بالقائمة كاملة وانسخ كل ملف
تجاوز للمشغّل ضمن مجموعة الاستعادة.
