ابدأ بنتيجة المستخدم التي فشلت وبأول خطأ ذي صلة. احتفظ بنسخة من `.env` الحالي
وقاعدة البيانات والتخزين والسجلات قبل إعادة إنشاء الخدمات. لا تحذف وحدات
التخزين ولا تنفّذ إعادة ضبط نظيفة كاختصار لاستكشاف الأخطاء وإصلاحها.

## جمع لقطة تشخيصية آمنة

نفّذ من مجلد عملية النشر. في مجلد أنشأه برنامج التثبيت الموجّه، احذف
`-f docker-compose.prod.yml`:

```bash
docker compose -f docker-compose.prod.yml ps
docker compose -f docker-compose.prod.yml logs migrate
docker compose -f docker-compose.prod.yml logs --since=15m server worker app
docker compose -f docker-compose.prod.yml config --services
```

لا تنشر ناتج `docker compose config` أو ملف `.env`؛ فقد تتضمن التهيئة المصيّرة
أسرارًا. عند طلب المساعدة، أرفق وسم Nibleaf وملخّصه الرقمي، وإصدار Compose،
والخدمة المتأثرة، والخطأ بعد تنقيحه، والسلوك المتوقع، والوقت الدقيق.

## فحوص الصحة والتشخيصات الخاصة

ينطبق وصف الصحة التالي على الصور التي تتضمن مسارات الصحة المحدّثة؛ قد تختلف
استجابة الإصدارات المثبّتة الأقدم أو لا يتوفر فيها مسار التفاصيل. تحقّق من مراجعة
الصورة المنشورة قبل إعداد المراقبة.

- **جاهزية API:** استخدم `http://127.0.0.1:4311/health` من داخل حاوية `server`.
  يعتمد Compose وCoolify على رمز HTTP: تكون الاستجابة `200` بعد تهيئة API
  والطوابير، و`503` أثناء بدء التشغيل أو الإيقاف. يحتوي JSON العام على `status`
  و`revision` الحالي فقط، ولا يعرض تفاصيل التخزين أو مزوّدي الخدمة.
- **بقاء العملية (liveness):** إذا فصلت المنصة هذا الفحص عن الجاهزية، فاستخدم
  فحص TCP لمنفذ API. لا تُعد تشغيل API يعمل لمجرد تعذّر فحص تخزين مطلوب صراحةً
  بصورة مؤقتة.
- **الخدمات الأخرى:** أبقِ `/health` على منفذ التطبيق `4310` والإدارة `4315`
  ومنفذ عمليات العامل الخاص `4312`. تواصل طبقة التطبيق وأداة التحقق من الإصدار
  استخدام `/api/app/health` وعقد المراجعة في `/health` الخاص بالتطبيق.
  أبقِ منفذ العامل خاصًا؛ إذ تتضمن استجابته الحالية تشخيصات الطوابير والبريد.
  يربطه Compose المبني من المصدر بعنوان loopback، وتبقيه قوالب الإنتاج وCoolify على الشبكة الداخلية.

للحصول على تشخيصات تخزين API والتحليلات، اضبط `INTERNAL_API_SECRET` في بيئة
حاوية API واطلب `/health/details` مع الترويسة `x-nibleaf-internal`. أعد استخدام
السر الداخلي الموجود إن كان مضبوطًا؛ لا تستبدل مفتاحًا قائمًا لتشخيص الصحة.
تمرّر قوالب المصدر والإنتاج وCoolify هذا السر. يعيد غياب السر أو عدم تطابقه أو
عدم ضبطه الرمز `401`، وتستخدم الاستجابات التفصيلية
`Cache-Control: private, no-store`.

```bash
docker compose -f docker-compose.prod.yml exec -T server sh -c \
  'curl -sS -H "x-nibleaf-internal: $INTERNAL_API_SECRET" http://127.0.0.1:4311/health/details'
```

يستخدم مسار التفاصيل رمز الجاهزية نفسه، لذلك يحذف المثال الخيار `curl -f`
لإظهار التشخيصات عند الاستجابة `503`. لا تضع السر في عنوان URL أو كود المتصفح
أو فحص عام أو سجل محادثة دعم. قد يجعل الوكيل أو المدخل المسار التفصيلي قابلًا
للوصول؛ لكنه يرفض الطلب دون ترويسة السر المطابقة. يحافظ وكيل لوحة التحكم
الافتراضي على `/api`: يُمرّر `/api/health/details` إلى المسار نفسه في API،
بينما يُسجّل معالج التفاصيل في جذر API على `/health/details`، لذلك لا تكشفه لوحة التحكم.
أما المدخل المخصص الذي يربط جذر API فيكشفه. أبقِ منفذ عمليات العامل خاصًا.

القيمة الافتراضية هي `STORAGE_REQUIRED_FOR_HEALTH=false`: تكون أخطاء فحص
الحاوية التخزينية تشخيصية ولا تمنع جاهزية API بعد تهيئته. عند ضبطها على `true`
يلزم نجاح فحص الحاوية التخزينية أيضًا لإرجاع `200`؛ وقد لا تملك مفاتيح الوصول
المقيّدة بالكائنات الصلاحية اللازمة على مستوى الحاوية. لا تؤثر CORS في الجاهزية.
اضبط الخيار في بيئة الحاوية؛ قد يحتاج ملف Compose مثبّت قديم إلى ملف تجاوز
مراجَع لتمريره دون تعديل أصل الإصدار المحمي بالمجموع الاختباري.

تُعاد محاولة أخطاء الشبكة وأخطاء المزوّد `5xx` بتراجع يصل إلى 30 ثانية بين
المحاولات، حتى إن تجاوز الانقطاع نافذة بدء التشغيل الأولى. تُسجّل الإخفاقات
المستمرة بمستوى debug بين تحذيرات تصدر في كل محاولة عاشرة. توقف بيانات الاعتماد
أو الصلاحيات المرفوضة عملية التهيئة المتأثرة مع تحذير واضح: أصلحها وأعد تشغيل API،
أو اضبط CORS خارجيًا واستخدم `STORAGE_AUTO_CORS=false`. تعرض الصحة التفصيلية
`storage.ready` و`storage.cors` و`storage.requiredForHealth`؛ وتعني `cors: null`
أن إعداد CORS التلقائي معطّل. لا تثبت هذه الفحوص نجاح الرفع من المتصفح عبر عنوان التخزين العام.

## المكدّس لا يبدأ

| العَرَض | السبب المرجح | الفحص التالي |
| --- | --- | --- |
| يخرج Compose قبل إنشاء الخدمات | قيمة مطلوبة في البيئة فارغة. | اقرأ خطأ الاستبدال وقارن `.env` بالقالب من الإصدار نفسه. |
| ينتظر التطبيق الخادم | فحص سلامة الخادم يفشل أو لم يكتمل `migrate`. | اقرأ سجل `migrate` ثم أول خطأ للخادم. |
| ترفض بيئة الإنتاج سر المصادقة | القيمة فارغة أو ضعيفة أو قيمة تجريبية افتراضية معروفة. | للتثبيت الجديد أنشئ قيمة مستقلة. للتثبيت القائم استعد السر الصحيح الحالي؛ لا تستبدل المفاتيح لإصلاح مشكلة تحميل البيئة. |
| سحب الصورة مرفوض أو الصورة مفقودة | الوسم غير موجود أو فشل الوصول إلى السجل. | تحقق من الوسم في صفحة الإصدار ونفّذ `docker compose pull` مباشرة. |
| يبلّغ السحب عن عدم وجود بيان مطابق، أو تخرج حاوية مع `exec format error` | المضيف ليس `linux/amd64`. لا تدعم الصورة المنشورة غير هذه البنية. | نفّذ `uname -m`. أي قيمة غير `x86_64` تحتاج إلى مضيف amd64. |
| يتوقف برنامج التثبيت مع `Unsupported architecture` | المضيف ليس `linux/amd64`. | استخدم مضيف amd64، ولا تلتفّ حول هذا الفحص. |
| يتوقف برنامج التثبيت مع `Existing installation` | يحتوي المجلد أو Docker على تثبيت Nibleaf قائم. | لا تحذفه لتجاوز الفحص. استخدم [دليل الترقية](/ar/self-hosting/upgrade-v0-2). |

لا تتخطَّ عمليات الترحيل بإزالة الاعتماديات من ملف Compose.

## لا يصبح API وعامل المعالجة جاهزين بعد الترقية

لا تصبح `server` و`worker` جاهزتين، وتنتظر `app` خدمة API، وتعرض السجلات:

```text
Unknown recurring configuration in analytics; complete the migration using the retained staged v5 image
```

بدأ v0.2.0 على جداول من v0.1.2، وغالبًا لأن الإصدار تغيّر من دون الترحيل المرحلي.
بياناتك سليمة. لا تحذف وحدة تخزين Dragonfly، ولا تُزِل المهام، ولا تُعد تشغيل برنامج
التثبيت. اتبع
[إذا تخطيت المرحلة الوسيطة](/ar/self-hosting/upgrade-v0-2#إذا-تخطيت-المرحلة-الوسيطة).

## فشل عمليات الرفع في المتصفح

يستخدم المتصفح `STORAGE_PUBLIC_ENDPOINT`، لا اسم مضيف Docker الداخلي. تحقق من
DNS وTLS وCORS للحاوية وبيانات الاعتماد ووضع نمط المسار والمضيف الموقّع. افتح
خطأ الشبكة في المتصفح وقارن مصدره بـ`APP_URL` و
`STORAGE_CORS_ALLOWED_ORIGINS`.

قد ينجح فحص سلامة التخزين الداخلي بينما يفشل مسار الرفع العام.

## البريد الإلكتروني لا يصل

افحص سجل عامل المعالجة (worker)، والتحقق من المُرسِل، وتدفق الرسائل في Postmark
أو عنوان SMTP، ومجلد البريد العشوائي لدى المستلم، ونشاط المزوّد. يتطلب تسجيل
الدخول دون كلمة مرور تسليم رمز لمرة واحدة. في غياب Postmark أو SMTP، يسجّل
عامل المعالجة رسائل بريد التطوير بدلًا من تسليمها في بيئة التطوير أو عندما
يكون التسليم اختياريًا فقط. يفشل التسليم المطلوب في الإنتاج إذا لم يُضبط
Postmark أو SMTP، ويعيد فحص سلامة عامل المعالجة 503 حتى يُضبط أحدهما. القيمة
الافتراضية لـ`EMAIL_DELIVERY_REQUIRED` هي `true`. لا تضبطها على `false` إلا عند إعداد
تسجيل الدخول عبر Google، إذ لا يمكن لأحد تلقي رمز بريدي من دون مزوّد.

## عملية نشر تبقى في طابور المهام أو تفشل

تحقق من سلامة عامل المعالجة واتصاله بطابور المهام، ثم اقرأ خطأ عملية النشر وسجل
العامل عند وقت النشر. يجب أن يواصل الموقع العام تقديم الإصدار السابق ذي الحالة
`READY`. صحّح السبب وانشر إلى الأمام؛ ولا تعدّل حالة قاعدة البيانات يدويًا.

## عملية تصدير أو Git تبقى في طابور المهام

تحقق مما إذا كان `WORKER_QUEUES` فارغًا أو يتضمن طابور `export` أو `git`
المطلوب. ثم افحص سلامة عامل المعالجة وسجل التشغيل أو العملية الدائم في لوحة
التحكم. بالنسبة إلى أعطال PDF وحدها، تحقق من `EXPORT_CHROMIUM_PATH` داخل عامل
المعالجة. وبالنسبة إلى أعطال Git، حافظ على سجل العملية والتعارض؛ وأعد المحاولة
عبر مسار التسوية الموثّق بدلًا من الدفع القسري إلى فرع التأليف.

لا يمكن لتغيير `GIT_CREDENTIAL_ENCRYPTION_KEY` إصلاح خطأ فك التشفير، وسيجعل
بيانات الاعتماد الحالية غير قابلة للقراءة. استعد المفتاح الصحيح أو اتبع تدويرًا
منضبطًا عبر قطع الاتصال وإعادة وصله.

## نطاق يعرض الموقع الخطأ

تحقق من DNS واسم الشهادة وحالة النطاق الأساسي وتمرير `Host` الأصلي وأهداف
النطاق الأساسي وCNAME المهيّأة. اختبر التطبيق مباشرة بترويسة المضيف المقصودة
من بيئة مشغّل موثوقة فقط. إذا استبدل الوكيل جميع مضيفي العملاء باسم المنبع
الداخلي، فلن يتمكن Nibleaf من تحديد المشروع.

## جميع الزوار يشتركون في حصة واحدة لتحديد المعدل

راجع [يرى القرّاء رسالة «طلبات كثيرة جدًا»](#يرى-القرّاء-رسالة-طلبات-كثيرة-جدًا) لمعرفة طريقة ضبط `INTERNAL_API_SECRET` وحساب `TRUSTED_PROXY_HOPS`.

## البحث لا يعثر على تعديل حديث

لا تدخل تغييرات المسودة في البحث العام حتى تصبح عملية النشر بالحالة `READY`.
تأكد من أن الصفحة منشورة وقابلة للفهرسة، وابحث عن عنوانها الدقيق، ثم عن عبارة
مميزة من متنها. بالنسبة إلى العربية، اختبر تنويعات الكتابة بعد التطبيع وراجع
[العربية واتجاه RTL](/ar/product/arabic-rtl).

بالنسبة إلى السلوك الحساس أمنيًا، أوقف استكشاف الأخطاء علنًا واستخدم مسار
الإبلاغ الخاص الوارد في ملف `SECURITY.md` بالمستودع.

## التحليلات غير متاحة أو المخطط قديم أو الترقية عالقة

قد يظل موقع التوثيق سليماً مع تعذر التحليلات. افحص حقل `analytics` في `/health` للخادم والعامل،
وافصل تنبيهاته عن تنبيهات الخدمات الأساسية. عند `unavailable`، تحقق من الشبكة وDNS وبيانات الاعتماد
واسم القاعدة وسجلات ClickHouse. أعد الاتصال ودع العامل يعيد المحاولة؛ لا تعد تشغيل القواعد ولا تمسح قوائم المهام.
راقب عمر أقدم مهمة وإعادة تشغيل المهام الفاشلة حتى لا يتحول الانقطاع إلى فجوات في السجل.

عند `schema_outdated`، تحقق من تشغيل العامل وتفعيل التحليلات وضبط `CLICKHOUSE_MIGRATE_ON_BOOT=true`،
ومن صلاحيات CREATE وALTER للكاتب. إذا عطلت الترقية التلقائية، شغّل `clickhouse-migrate` بإعدادات Postgres
وقاعدة ClickHouse نفسها. نجاح اختبار الاتصال وحده لا يثبت اكتمال المخطط.

للترقيات العالقة، افحص سجلات العامل و`pg_stat_activity` و`pg_locks` للأقفال الاستشارية،
و`system.processes` و`system.mutations` في ClickHouse. قد يكون مالك القفل عاملاً آخر أو الأداة اليدوية.
لا تمسح سجلات إصدارات المخطط ولا تتجاوز القفل أثناء عمل أمر مخطط.
تأكد من توقف العملية المالكة واستعلامها قبل إعادة المحاولة.

عند ضغط مساحة القرص، افحص `system.parts` بحسب القاعدة والجدول، ووحدتي البيانات والسجلات.
يعطل الإعداد المرفق السجلات الكثيفة الجديدة ويدوّر السجلات النصية، لكنه لا يزيل جداول النظام القديمة.
راجعها مع المشغّل قبل تنظيف محدد. انقل النسخ خارج المضيف ثم راجع الاحتفاظ؛
فالدمج يحتاج إلى مساحة حرة، وحذف TTL غير فوري. لا تحذف ملفات بيانات ClickHouse يدوياً،
ولا تشغّل OPTIMIZE FINAL واسعاً على مضيف ممتلئ، ولا تمسح المهام لمجرد تحسين مؤشر الحالة.
إذا كانت الحالة `ok` ولم تصل أحداث جديدة، افحص `ANALYTICS_HASH_SALT` قبل تشخيص الشبكة.
عند تفعيل تحليلات ClickHouse وغياب الملح، تسقط الأحداث رغم سلامة المخطط.
أعد سر النشر الحالي، ولا تستبدله لمعالجة متغير بيئة مفقود.
قد تكون نتيجة فحص المخطط مخزنة منذ عشر ثوان، بينما تظهر حالة ترقية العامل فوراً.
## لا يؤثر إعداد موجود في .env

تحقق من قائمة ملفات Compose والصورة المنشورة. يزوّد `.env` الاستبدال في Compose،
ولا يصبح تلقائياً بيئة الحاوية. لا يمرّر ملف v0.2.0 الإنتاجي المثبّت إعدادات
ClickHouse والبحث أو قائمة الطوابير أو إعدادات التصدير أو حدود كتابة MCP
اللاحقة. استخدم ملف تجاوز مراجعاً وصورة مطابقة وأعد إنشاء الخدمة المعنية.
لا تطبع البيئة الكاملة أو الإعداد النهائي في طلب دعم؛ راجع
[مرجع تمرير الإعدادات](/ar/reference/environment-variables).

## اختفاء Ask AI أو تعذره أو توقفه المبكر

افحص تفعيل الذكاء الاصطناعي في الموقع واختيار المزوّد وتوفر مفتاح التشفير على
API والعامل واتصال Qdrant وفهرس READY للنشر الحالي. حفظ اتصال مساحة العمل
لا يختاره، ولا يعود المزوّد المختار إلى مفتاح النسخة تلقائياً. OAuth الخاص
باعتماد نموذج OpenAI أو ChatGPT غير متاح؛ اتصال MCP عبر OAuth أمر مختلف.

لا يفحص تحقق الدليل رصيد المزوّد ولا ينفذ استدلالاً. جرّب سؤالاً وهمياً بعد
التفعيل. لا تستبدل مفتاح التشفير لإصلاح اعتماد غير مقروء؛ استعد المفاتيح الحالية.

تعرض المحادثة رموزاً ثابتة داخل البث: يعني `conversation_limit` بدء محادثة
جديدة؛ و`quota_exhausted` نفاد حصة الإجابات اليومية؛ و`budget_exhausted` ميزانية
رموز المشروع؛ و`rate_limited` حد الطلبات القصير. قد يعني `unavailable` مشكلة
إعداد مزوّد أو فهرس أو مخزن الحصص. افحص معرّف طلب API وتحذير الميزانية عند البدء.
يختلف حد ملف البحث الإضافي الحالي 60000 عن افتراضي المخطط 150000، وقد يرفض
جولة كبيرة قبل استدعاء المزوّد.

إذا عملت المحادثة وغاب السجل، افحص وضع التحليلات وطابور `analytics` وصحة
ClickHouse ومخططه و`ANALYTICS_HASH_SALT` وإعداد النص والموافقة. يجب أن يحل
API والعامل مفتاح نقل المحادثة نفسه؛ لا تغيّره مع وجود مهام مشفّرة معلّقة.
لا تثبت صحة مخطط ClickHouse حفظ جولة.

لأخطاء MCP استخدم [دليل أخطائه](/ar/self-hosting/mcp). إذا فشل تحديث التدقيق
بعد كتابة، فأعد قراءة الهدف قبل المحاولة؛ قد تكون المسودة تغيرت بالفعل. تشمل
معاينة النشر المشروع كاملاً.

## يرى القرّاء رسالة «طلبات كثيرة جدًا»

**العَرَض:** يتلقى القرّاء أو أدوات فحص الروابط أو محركات البحث الرمز `429 Too Many Requests`، مع أن كل شخص يقرأ صفحات قليلة فقط.

**السبب:** تحدّ واجهة API من الطلبات العامة لكل عنوان زائر (`RATE_LIMIT_PUBLIC_PER_MIN`، وقيمته الافتراضية 300 طلب في الدقيقة). تعرض حاوية التطبيق الصفحة المنشورة وتطلب البيانات من واجهة API نيابةً عن القارئ. ولا تثق واجهة API بعنوان القارئ الذي يمرّره التطبيق إلا عندما تُضبط `INTERNAL_API_SECRET` على القيمة نفسها في خدمتي التطبيق وواجهة API. وبدونها يتشارك كل القرّاء عنوان حاوية التطبيق وحصة واحدة قدرها 300 طلب في الدقيقة.

**الحل:**

1. أنشئ سرًّا، مثلًا بالأمر `openssl rand -hex 32`.
2. اضبط `INTERNAL_API_SECRET` على القيمة نفسها لخدمتي التطبيق وواجهة API، ثم أعد إنشاءهما.
3. اضبط `TRUSTED_PROXY_HOPS` على عدد **العناوين التي تظهر بعد عنوان العميل** في `X-Forwarded-For` في طلب عادي، **بما فيها العناوين الخاصة**. يسجّل كل وكيل العنوان الذي استلم منه الطلب، لذا تظهر عناوين شبكة CDN أو الحافة وموازن الحمل والوكلاء العكسيين بعد محطة واحدة. اضبط **القيمة نفسها على خدمتي التطبيق وواجهة API**؛ والقيمة الافتراضية `0`. اضبط بوابة الدخول لإزالة ترويسات التمرير غير الموثوقة، وافحص السلسلة الفعلية التي تصل إلى كل خدمة قبل اختيار العدد.
4. لا ترفع `RATE_LIMIT_PUBLIC_PER_MIN` إلا إذا ظل قرّاء حقيقيون يصلون إلى الحد.

يمرّر ملفا Compose للإنتاج وCoolify (`docker-compose.prod.yml`
و`docker-compose.coolify.yml`) كلا الإعدادين إلى خدمتي التطبيق وواجهة API. أما
ملف المصدر `docker-compose.yml` فلا يمرّر أيًّا منهما، لذا أضف ملف تجاوز بجانبه. يقرأ
`docker compose` الملف `docker-compose.override.yml` تلقائيًا؛ وإذا كنت تشغّل الأمر مع
`-f docker-compose.yml` فأضف أيضًا `-f docker-compose.override.yml`:

```yaml
# docker-compose.override.yml, next to the source docker-compose.yml
services:
  server:
    environment:
      INTERNAL_API_SECRET: ${INTERNAL_API_SECRET:-}
      TRUSTED_PROXY_HOPS: ${TRUSTED_PROXY_HOPS:-0}
  app:
    environment:
      INTERNAL_API_SECRET: ${INTERNAL_API_SECRET:-}
      TRUSTED_PROXY_HOPS: ${TRUSTED_PROXY_HOPS:-0}
```

**أمثلة توضيحية:** العناوين التالية للشرح. يمثل `9.9.9.9` قيمة مزوّرة أرسلها
العميل، و`203.0.113.7` عنوانه الحقيقي، و`198.51.100.x` عناوين عامة لشبكة CDN أو
موازن الحمل، و`172.17.0.1` وكيلًا عكسيًا بعنوان خاص. يسجّل nginx الخاص أمام Nibleaf
عنوان العميل، لذا تكون الترويسة مع nginx وحده `9.9.9.9, 203.0.113.7` ولا يلي العميلَ
أي عنوان: استخدم `0`.

| الترويسة المستقبلة | العناوين بعد عنوان العميل | `TRUSTED_PROXY_HOPS` | عنوان العميل المختار |
| --- | --- | --- | --- |
| `9.9.9.9, 203.0.113.7` | لا توجد؛ nginx خاص فقط | `0` | `203.0.113.7` |
| `9.9.9.9, 203.0.113.7` | لا توجد، لكن القيمة أعلى من اللازم | `1` | `9.9.9.9` — مزوّر |
| `9.9.9.9, 203.0.113.7, 198.51.100.9` | عنوان واحد: CDN أو الحافة | `1` | `203.0.113.7` |
| `9.9.9.9, 203.0.113.7, 198.51.100.9, 198.51.100.10` | عنوانان: CDN أو الحافة وموازن الحمل | `2` | `203.0.113.7` |
| `9.9.9.9, 203.0.113.7, 198.51.100.9, 172.17.0.1` | عنوانان: Cloudflare ثم nginx المضيف (خاص)، خلف Traefik | `2` | `203.0.113.7` |
| `9.9.9.9, 203.0.113.7, 198.51.100.9, 172.17.0.1` | عنوانان، لكن احتُسب العام وحده | `1` | `198.51.100.9` — يتشارك كل القرّاء عنوان Cloudflare |

يحذف كلا المحلّلين أولًا العدد المضبوط من العناصر الأخيرة للترويسة، مع الإبقاء على
عنصر واحد على الأقل، ثم يفحصان من اليمين إلى اليسار متجاوزَين العناوين الخاصة،
ويختاران أول عنوان عام. لهذا يجب احتساب العناوين الخاصة عندما يسبقها عنوان عام. وإذا
كانت كل العناوين بعد عنوان العميل خاصة وكان عنوان القارئ نفسه عامًا، فاحتسابها
وعدمه يعطيان النتيجة نفسها. وإذا كانت عناوين القرّاء خاصة (شبكة داخلية أو VPN)
فاحتسبها أيضًا. تحقق من الترويسات التي تصل
فعليًا إلى كل خدمة؛ لا يكفي عدد الوكلاء في مخطط الشبكة. قد يحذف العدد الأعلى
من الصحيح عنوان العميل الحقيقي ويختار قيمة زوّرها المهاجم، فيتمكن من تغيير
هويته المستخدمة لتحديد المعدل. لا تستخدم رفع العدد وسيلة لإخفاء استجابات `429`.

**التحقق:** طابق العنوان المختار مع سلسلة الترويسات الفعلية، بما فيها قيمة
يسارية مزوّرة عمدًا، ثم افتح بضع صفحات من شبكتين مختلفتين. يجب ألا تظهر لأيٍّ
منهما `429`.
