Start with the failed user outcome and the first relevant error. Preserve the
current `.env`, database, storage, and logs before recreating services. Do not
delete volumes or run a clean reset as a troubleshooting shortcut.

## Collect a safe diagnostic snapshot

Run from the deployment directory. In a guided-installer directory, omit
`-f docker-compose.prod.yml`:

```bash
docker compose -f docker-compose.prod.yml ps
docker compose -f docker-compose.prod.yml logs migrate
docker compose -f docker-compose.prod.yml logs --since=15m server worker app
docker compose -f docker-compose.prod.yml config --services
```

Do not post `docker compose config` or `.env`; rendered configuration can contain
secrets. When asking for help, include the Nibleaf tag and digest, Compose
version, affected service, redacted error, expected behavior, and exact time.

## Health probes and private diagnostics

The following health contract applies to images containing the updated health
routes; older pinned releases may have a different response or lack the detailed
route. Check the deployed image revision before configuring monitoring.

- **API readiness:** use `http://127.0.0.1:4311/health` inside the `server`
  container. Compose and Coolify use the HTTP status: `200` after API/queue
  initialization, `503` while starting or shutting down. The public JSON contains
  only `status` and the existing `revision`; it exposes no storage or provider detail.
- **Process liveness:** if your platform separates liveness from readiness, use
  a TCP check on the API listener. Do not restart a live API just because an
  explicitly required storage check is temporarily unavailable.
- **Other services:** retain `/health` on app port `4310`, admin port `4315`,
  and the private worker operations port `4312`. The app wrapper and release
  verifier still use `/api/app/health` and the app's `/health` revision contract.
  Keep the worker port private: its existing body contains queue/email diagnostics.
  Source Compose binds it to loopback; production/Coolify keep it on their internal network.

For API storage and analytics diagnostics, set `INTERNAL_API_SECRET` in the API
container environment and request `/health/details` with the
`x-nibleaf-internal` header. Reuse the existing internal secret where configured;
do not replace an existing key to diagnose health. Source, production, and
Coolify templates forward this secret. Missing, wrong, or unset secrets return
`401`; detailed responses use `Cache-Control: private, no-store`.

```bash
docker compose -f docker-compose.prod.yml exec -T server sh -c \
  'curl -sS -H "x-nibleaf-internal: $INTERNAL_API_SECRET" http://127.0.0.1:4311/health/details'
```

The detailed route uses the same readiness HTTP status, so the example omits
`curl -f` to show diagnostics during `503` responses. Never place the secret in a
URL, browser code, public probe, or support transcript. A proxy or ingress can
make the detailed route reachable; it fails closed without the matching secret
header. The dashboard's standard proxy preserves `/api`: `/api/health/details`
is forwarded to that same API path, while the detailed handler is registered at
API-root `/health/details`, so the dashboard doesn't expose it. A custom ingress
that maps the API root does. Keep the worker operations listener private.

`STORAGE_REQUIRED_FOR_HEALTH=false` is the default: failed bucket checks are
diagnostic and do not block an initialized API. With `true`, a successful bucket
check is also required for `200`; object-only credentials may lack the necessary
bucket-level permission. CORS never gates readiness. Set the option in the
container environment; an older pinned Compose file may need a reviewed override
to forward it without editing its checksummed release asset.

Network and provider `5xx` failures retry with backoff capped at 30 seconds,
including outages longer than the initial startup window. Continuing failures
use debug logs between warnings on every tenth attempt. Rejected credentials
or permissions stop the affected bootstrap operation with a warning: fix the
credentials/permissions and restart the API, or provision CORS externally and set
`STORAGE_AUTO_CORS=false`. Detailed health exposes `storage.ready`, `storage.cors`,
and `storage.requiredForHealth`; `cors: null` means automatic CORS is disabled.
These checks do not prove that browser uploads work through the public storage endpoint.

## The stack does not start

| Symptom | Likely cause | Next check |
| --- | --- | --- |
| Compose exits before creating services | A required environment value is empty. | Read the interpolation error and compare `.env` with the template from the same release. |
| App waits for the server | Server health is failing or `migrate` did not complete. | Read `migrate`, then the first server error. |
| Production refuses authentication secret | The value is empty, weak, or a known demo default. | Generate a fresh independent value and restart only after updating `.env`. |
| Image pull is denied or missing | The tag does not exist or registry access failed. | Confirm the tag on the release page and run `docker compose pull` directly. |
| Pull reports no matching manifest, or a container exits with `exec format error` | The host is not `linux/amd64`. The published image supports only that architecture. | Run `uname -m`. Anything other than `x86_64` needs an amd64 host. |
| The installer stops with `Unsupported architecture` | The host is not `linux/amd64`. | Use an amd64 host. Do not work around the check. |
| The installer stops with `Existing installation` | The directory or Docker already holds a Nibleaf installation. | Do not remove it to get past the check. Use the [upgrade guide](/self-hosting/upgrade-v0-2). |

Do not skip migrations by removing dependencies from the Compose file.

## The API and worker do not become ready after an upgrade

`server` and `worker` do not become ready, `app` waits for the API, and the logs show:

```text
Unknown recurring configuration in analytics; complete the migration using the retained staged v5 image
```

v0.2.0 started on schedules from v0.1.2, usually because the version was changed
without the staged migration. Your data is intact. Do not delete the Dragonfly
volume, remove jobs, or re-run the installer. Follow
[If you skip the staged step](/self-hosting/upgrade-v0-2#if-you-skip-the-staged-step).

## Uploads fail in the browser

The browser uses `STORAGE_PUBLIC_ENDPOINT`, not the internal Docker hostname.
Confirm DNS, TLS, bucket CORS, credentials, path-style mode, and the signed host.
Open the browser network error and compare its origin with `APP_URL` and
`STORAGE_CORS_ALLOWED_ORIGINS`.

An internal storage health check can pass while the public upload path fails.

## Email does not arrive

Check the worker log, sender verification, Postmark message stream or SMTP URL,
recipient spam folder, and provider activity. Passwordless sign-in requires
delivery of a one-time code. In development, or when delivery is optional, the
worker can log development mail instead. Required production delivery fails
when neither Postmark nor SMTP is configured, and the worker health check returns
503 until one is. `EMAIL_DELIVERY_REQUIRED` defaults to `true`. Set it to `false` only
when Google sign-in is configured, because nobody can receive an email code without a
provider.

## A publish stays queued or fails

Check worker health and queue connectivity, then read the deployment error and
worker log at the publish time. The public site should continue serving the
previous ready version. Correct the cause and publish forward; do not modify the
database status manually.

## An export or Git operation stays queued

Check whether `WORKER_QUEUES` is empty or includes the required `export` or `git`
queue. Then inspect worker health and the durable run or operation record in the
dashboard. For PDF-only failures, verify `EXPORT_CHROMIUM_PATH` inside the worker.
For Git failures, preserve the operation and conflict record; retry through the
documented reconciliation flow instead of force-pushing the authoring branch.

Changing `GIT_CREDENTIAL_ENCRYPTION_KEY` cannot repair a decryption error and
will make existing credentials unreadable. Restore the correct key or follow a
controlled disconnect/reconnect rotation.

## A domain serves the wrong site

Confirm DNS, certificate name, primary-domain status, original `Host` forwarding,
and the configured base/CNAME targets. Test the app directly with the intended
host header only from a trusted operator environment. A proxy that replaces all
customer hosts with its internal upstream name prevents project resolution.

## Every visitor shares one rate-limit bucket

Capture the forwarding chain at the ingress. Configure the proxy to discard
untrusted forwarded headers, then set `TRUSTED_PROXY_HOPS` to the number of
public proxies that actually append addresses. Do not increase the value until
requests stop failing; an excessive value weakens address attribution.

## Search misses a recent edit

Draft changes do not enter public search until a deployment is ready. Confirm
the page is published and indexable, search its exact title, then a distinctive
body phrase. For Arabic, test normalized spelling variants and consult
[Arabic and RTL](/product/arabic-rtl).

For security-sensitive behavior, stop public troubleshooting and use the
private reporting path in the repository's `SECURITY.md`.

## Analytics unavailable, outdated, or stuck

The docs site can remain healthy while analytics is unavailable. Inspect the
`analytics` field on API and worker `/health`; keep it separate from core alarms.
For `unavailable`, check network/DNS, credentials, database name and ClickHouse
logs. Restore connectivity and let the worker retry; do not restart databases or
clear queues. Watch oldest pending jobs and failed-job replay so outages do not
silently become missing history.

For `schema_outdated`, check that a worker is running, analytics is enabled and
`CLICKHOUSE_MIGRATE_ON_BOOT=true`. Check writer CREATE/ALTER permissions. Run the
explicit `clickhouse-migrate` command with the same Postgres and ClickHouse
database settings if automatic migrations are disabled. A successful ping alone
does not establish schema currency.

For stuck migrations, inspect worker migration logs, `pg_stat_activity` and
`pg_locks` (advisory locks), and ClickHouse `system.processes` and
`system.mutations`. Lock holders may legitimately be another worker or the CLI.
Do not clear migration-version records or kill locks to bypass a running DDL
operation. Confirm the owning process and query have stopped before retrying.

For disk pressure, inspect `system.parts` by database/table and both the data and
log volumes. Bundled configuration disables new noisy system logs and rotates
text logs; old system tables are not automatically removed. Review them with an
operator before targeted cleanup. Copy backups off-host, then review retention;
TTL merges need free space and are asynchronous. Never delete ClickHouse data
files, run broad OPTIMIZE FINAL on a full host, or erase queues to make health green.
If health is `ok` but no new events arrive, check `ANALYTICS_HASH_SALT` before
network debugging. With ClickHouse analytics enabled and no salt, events are
dropped even though schema health is healthy. Restore the existing deployment
secret; never replace it to fix a missing environment variable. Schema health
results can be up to ten seconds old; the worker migration flag is immediate.
