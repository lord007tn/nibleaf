You cannot reach v0.2.0 from v0.1.2 by changing the image tag. v0.1.2 stores its
recurring jobs as BullMQ 5 repeat definitions, and v0.2.0 runs BullMQ 6, which
refuses them. The upgrade is two hops: migrate the schedules from a staged image,
then move to v0.2.0. When you finish, your data, `.env`, Compose project name, and
volumes are unchanged, and all four recurring jobs run as Job Schedulers.

## Who needs this guide

Follow this guide if you self-host v0.1.2 with the guided installer or
`docker-compose.prod.yml`.

- **New installation:** you need none of this. Use the
  [self-hosted quickstart](/getting-started/self-hosted).
- **Older than v0.1.2:** reach v0.1.2 first. This path starts from v0.1.2.
- **Other deployments**, such as `docker-compose.coolify.yml` or a source build:
  the order is the same, but service and volume names differ. Adapt the commands
  and rehearse on a copy first.

Start only after v0.2.0 appears on the
[releases page](https://github.com/lord007tn/nibleaf/releases). Do not re-run the
installer to upgrade: it is for new installations only.

## What changes

| Area | Change | What you do |
| --- | --- | --- |
| Recurring jobs | BullMQ 5 repeat definitions become BullMQ 6 Job Schedulers. | Run the staged migration. |
| Database | Seven Prisma migrations run through the `migrate` service. They are forward-only. | Take a backup. The migrations run on start. |
| Compose file | New `MCP_*` and `INTEGRATION_*` passthroughs. Changing only the version misses them. | Replace the file with the release's verified copy. |
| Integrations | Stored credentials use a dedicated encryption key. | Add `INTEGRATION_CREDENTIAL_ENCRYPTION_KEY` to `.env`. |
| AI writing assist | v0.2.0 reads `OPENROUTER_API_KEY`, not `OPENAI_API_KEY`. | See [After the upgrade](#after-the-upgrade) if you use it. |
| Platform | Prisma 7, Vite 8, and TypeScript 7 are inside the image. | Nothing. |

The seven migrations are:

1. `20260823120000_add_git_file_ownership`
2. `20260823143000_native_better_auth_admin`
3. `20260823180000_search_configuration_diagnostics`
4. `20260823210000_usage_metering`
5. `20260823220000_project_addons`
6. `20260823230000_add_project_integrations`
7. `20260823240000_mcp_control_plane`

## Before you start

Confirm each of these first:

- **A tested restore.** Follow [back up and restore](/self-hosting/backups-upgrades)
  and prove a restore in isolation. Step 5 takes the final backup.
- **A maintenance window.** The dashboard, the API, and published sites are offline
  from step 3 to step 11, because the `app` service serves published sites.
- **Disk space.** You need room for two more images, a database dump, and a storage
  archive. Check with `df -h .` and `docker system df`.
- **The amd64 architecture.** The published image is `linux/amd64` only. `uname -m`
  must print `x86_64`.
- **A sign-in path.** Sign-in uses email codes, or Google when configured. `.env`
  needs a value for `POSTMARK_API_KEY` or `SMTP_URL`. If you only use Google
  sign-in, also set `EMAIL_DELIVERY_REQUIRED=false`. Otherwise the worker reports
  unhealthy: its health check returns 503 when required email delivery has no
  provider.
- **One Bash session.** Run every step in the same shell from the deployment
  directory, because later steps use the variables and functions from step 1. Stop
  at the first command that fails.

## Upgrade step by step

### 1. Prepare the shell

Open the deployment directory. In a repository checkout, tell Compose to use the
production file, because `docker-compose.yml` there is the source-build stack:

```bash
export COMPOSE_FILE=docker-compose.prod.yml
```

Skip that command in a guided-installer directory, where the file is already
`docker-compose.yml`.

Define the staged image and a function that runs a command from it:

```bash
STAGE=sha-33cb19838cf8ea89889bcaafba5d63596e6f6c64
stage() {
  NIBLEAF_VERSION="$STAGE" docker compose run --rm --no-deps -T --workdir /app --entrypoint pnpm worker exec tsx "$@"
}
```

The image has no queue pause command, so create a small helper. It touches only the
two queues that hold recurring jobs and prints no connection details:

```bash
cat > nibleaf-queues.ts <<'EOF'
import { Queue } from 'bullmq';
import { producerConnectionConfig } from '../src/redis';
import { getQueueName } from '../src/utils/queue';

const action = process.argv[2];
const queues = ['analytics', 'export'].map(
  (name) => new Queue(getQueueName(name), { connection: producerConnectionConfig, skipMetasUpdate: true }),
);
for (const queue of queues) queue.on('error', () => undefined);

try {
  for (const queue of queues) {
    if (action === 'pause') await queue.pause();
    if (action === 'resume') await queue.resume();
    const [paused, active, waiting] = await Promise.all([queue.isPaused(), queue.getActiveCount(), queue.getWaitingCount()]);
    console.log(JSON.stringify({ queue: queue.name, paused, active, waiting }));
  }
} catch {
  console.error('Queue command failed. Leave the queues as they are and retry.');
  process.exitCode = 1;
} finally {
  await Promise.all(queues.map((queue) => queue.close()));
}
EOF
queues() {
  docker compose run --rm --no-deps -T \
    -v "$PWD/nibleaf-queues.ts:/app/packages/bullmq/scripts/nibleaf-queues.ts:ro" \
    worker node --import tsx packages/bullmq/scripts/nibleaf-queues.ts "$1"
}
```

Confirm where you are starting from:

```bash
grep '^NIBLEAF_VERSION=' .env
docker compose ps
```

**Expected:** the version is `v0.1.2` and all long-running services are healthy.

### 2. Download both images

Pull them now so the outage does not include the download:

```bash
NIBLEAF_VERSION="$STAGE" docker compose pull worker
docker image inspect --format '{{json .RepoDigests}}' "ghcr.io/lord007tn/nibleaf:$STAGE"
docker pull ghcr.io/lord007tn/nibleaf:v0.2.0
```

**Expected:** the staged image digest is
`sha256:880938a6ab865487f0b85733eeb2c20da06de34dcce1bdb5a8f35f694e4a3da8`. Stop if it
differs. This image is a commit build, not a release: use it for the schedule
migration only and never run it as your service.

### 3. Stop the services that create jobs

The outage starts here:

```bash
docker compose --profile admin stop app admin server
```

**Expected:** `docker compose ps` lists only `postgres`, `dragonfly`, `maxio`, and
`worker`.

### 4. Pause and quiet the queues

Give the worker a minute or two to finish what is already running. Then pause the
queues, stop the worker, and check the result:

```bash
NIBLEAF_VERSION="$STAGE" queues pause
docker compose stop worker
NIBLEAF_VERSION="$STAGE" queues status
```

**Expected:** two lines, one for each queue, with `"paused":true`, `"active":0`, and
`"waiting":0`.

The migration refuses to run unless both queues are paused with no active or waiting
jobs. If a count is not zero, let the work finish and try again. The export
dispatcher runs every minute, so a job can land in `waiting` between the pause and
the worker stopping. Never delete jobs to reach zero:

```bash
docker compose start worker
NIBLEAF_VERSION="$STAGE" queues resume
```

Wait until the jobs are done, then repeat this step just after the start of a
minute.

### 5. Take the final backup

Keep `STAMP` from this step. A rollback needs it:

```bash
mkdir -m 700 -p backups
STAMP=$(date +%Y%m%d-%H%M%S)
cp -p .env "backups/env-$STAMP"
cp -p "${COMPOSE_FILE:-docker-compose.yml}" "backups/compose-$STAMP.yml"
docker compose exec -T postgres pg_dump -U nibleaf -d nibleaf --format=custom > "backups/nibleaf-db-$STAMP.dump"
docker run --rm -v nibleaf_nibleaf-maxio:/data:ro -v "$PWD/backups":/backup alpine:3.22 tar czf "/backup/nibleaf-storage-$STAMP.tar.gz" -C /data .
ls -lh backups
```

**Expected:** four new non-empty files. If you use external R2 or S3 storage, skip the
`docker run` line and rely on your provider's backup. Copy the files off this host
before you continue. `backups/env-*` contains secrets, so protect it accordingly.

### 6. Run the migration as a dry run

```bash
stage packages/bullmq/scripts/migrate-schedules.ts
```

**Expected:** JSON with `"applied": false` and these four entries. This command
changes nothing. v0.1.2 has three legacy definitions; the fourth schedule is new in
v0.2.0, so both of its values are `false`:

| Schedule | `legacy` | `scheduler` |
| --- | --- | --- |
| `rollup-analytics-daily` | `true` | `false` |
| `reconcile-usage-periods` | `false` | `false` |
| `dispatch-export-schedules` | `true` | `false` |
| `cleanup-exports` | `true` | `false` |

Stop if the command reports an unknown or unexpected configuration. Do not work
around it.

### 7. Apply the migration

```bash
stage packages/bullmq/scripts/migrate-schedules.ts --apply
```

**Expected:** JSON with `"applied": true`. The tool creates and verifies every new
schedule before it removes any old one, so you can safely run it again after a
failure. If it reports that queues must be paused with no active or waiting jobs, go
back to step 4.

### 8. Verify the schedules

```bash
stage packages/bullmq/scripts/migrate-schedules.ts
```

**Expected:** all four entries show `"scheduler": true` and `"legacy": false`. Do not
continue until they do.

### 9. Replace the Compose file

Download the release's Compose file and verify it. Keep `.env`, the Compose project
name, and the volume names exactly as they are:

```bash
d=$(mktemp -d)
curl -fsSLo "$d/docker-compose.yml" https://github.com/lord007tn/nibleaf/releases/download/v0.2.0/docker-compose.yml
curl -fsSLo "$d/SHA256SUMS" https://github.com/lord007tn/nibleaf/releases/download/v0.2.0/SHA256SUMS
(cd "$d" && grep '  docker-compose.yml$' SHA256SUMS | sha256sum -c -)
cp "$d/docker-compose.yml" "${COMPOSE_FILE:-docker-compose.yml}"
```

**Expected:** `docker-compose.yml: OK`. Stop if the check fails.

### 10. Update `.env`

Set the new version, and add the integrations key if it is missing. The key is
written to `.env` and never printed:

```bash
sed -i "s/^NIBLEAF_VERSION=.*/NIBLEAF_VERSION='v0.2.0'/" .env
grep -Eq '^INTEGRATION_CREDENTIAL_ENCRYPTION_KEY=.+' .env || printf "INTEGRATION_CREDENTIAL_ENCRYPTION_KEY='%s'\n" "$(openssl rand -base64 32)" >> .env
grep '^NIBLEAF_VERSION=' .env
docker compose config --images
```

**Expected:** `NIBLEAF_VERSION` is `v0.2.0` and every Nibleaf image in the list ends
with `:v0.2.0`.

### 11. Start v0.2.0

```bash
docker compose pull
docker compose up -d
```

If you run the admin panel, use `docker compose --profile admin up -d` instead. The
`migrate` service applies the seven migrations before the API and the worker start.

Verify the database and the services:

```bash
docker compose ps -a
docker compose logs migrate
docker compose exec -T postgres psql -U nibleaf -d nibleaf -Atc 'SELECT migration_name FROM _prisma_migrations ORDER BY migration_name DESC LIMIT 7'
docker compose exec -T server curl -fsS http://127.0.0.1:4311/health
docker compose exec -T worker curl -fsS http://127.0.0.1:4312/health
```

**Expected:**

- long-running services are healthy, and `migrate` exited with code 0;
- the `migrate` log ends with `[nibleaf] migrate complete`;
- the query lists the seven migrations above;
- the worker health response shows `"status":"ok"`.

### 12. Resume the queues

The queues stay paused through the upgrade, and a healthy worker does not reveal
that. Skip this step and exports and analytics jobs silently stop:

```bash
queues resume
queues status
rm nibleaf-queues.ts
```

**Expected:** both queues show `"paused":false`. Waiting counts should fall to zero as
the worker catches up.

### 13. Test the product

Sign in with a real code, upload one image, publish a two-page project, search for
the second page while signed out, open a public page, and download one export.
Then record the image digest with your upgrade notes:

```bash
docker image inspect --format '{{json .RepoDigests}}' ghcr.io/lord007tn/nibleaf:v0.2.0
```

Keep the staged image and the backup until you no longer need to roll back.

## If you skip the staged step

If v0.2.0 starts on the old schedules, the API and the worker exit at startup and
Compose restarts them in a loop. `docker compose ps` shows `server` and `worker`
restarting, and `app` never starts because it waits for the API. The logs show:

```text
Unknown recurring configuration in analytics; complete the migration using the retained staged v5 image
```

The worker reports the same error for the `export` queue. The `migrate` service has
already run by this point, so the database is on v0.2.0.

Do not delete the Dragonfly volume, remove jobs, or re-run the installer. Your data is
intact. Set up the shell from step 1, then stop the crashing services:

```bash
docker compose stop server worker
```

Run steps 4 to 8, then skip steps 9 and 10, which are already done. Finish with steps
11 to 13. If you cannot bring the queues to zero, [roll back](#roll-back).

## Roll back

There are no down migrations, so rolling back v0.2.0 means restoring the pre-upgrade
backup. Rolling back the schedules alone is not enough. Restoring Postgres alone is
not enough either, because the schedules live in Dragonfly, which the backup does not
include. Do both, in this order.

Define `STAGE`, `stage`, and `queues` from step 1, and set `STAMP` to the value from
step 5. If you already deleted `nibleaf-queues.ts`, create it again.

### Restore the schedules

Stop the application services and quiet the queues:

```bash
docker compose --profile admin stop app admin server worker
NIBLEAF_VERSION="$STAGE" queues pause
NIBLEAF_VERSION="$STAGE" queues status
```

**Expected:** both queues are paused with `"active":0` and `"waiting":0`. If they are
not, use the retry in step 4.

Move the schedules back, then check them:

```bash
stage packages/bullmq/scripts/migrate-schedules.ts --rollback
stage packages/bullmq/scripts/migrate-schedules.ts --rollback --apply
stage packages/bullmq/scripts/migrate-schedules.ts
```

**Expected:** all four entries show `"legacy": true` and `"scheduler": false`. v0.1.2
does not know `reconcile-usage-periods`. It handles that job as its normal retention
cleanup, and the next upgrade migrates it again.

Restore the previous configuration:

```bash
cp -p "backups/compose-$STAMP.yml" "${COMPOSE_FILE:-docker-compose.yml}"
cp -p "backups/env-$STAMP" .env
```

### Restore the data

Skip this section only if you never reached step 11, because then no database
migration ran.

Move the upgraded database aside instead of dropping it, then restore into an empty
one. Do not use `pg_restore --clean` here: tables added by the migrations can block
it. Anything written after step 5 stays in the renamed database and is not restored:

```bash
docker compose exec -T postgres psql -U nibleaf -d postgres -c 'ALTER DATABASE nibleaf RENAME TO nibleaf_failed_upgrade'
docker compose exec -T postgres psql -U nibleaf -d postgres -c 'CREATE DATABASE nibleaf'
docker compose exec -T postgres pg_restore -U nibleaf -d nibleaf < "backups/nibleaf-db-$STAMP.dump"
```

Restore bundled storage. This replaces the current objects, so uploads made after
step 5 are lost. If you use external storage, restore it through your provider:

```bash
docker compose stop maxio
docker run --rm -v nibleaf_nibleaf-maxio:/data -v "$PWD/backups":/backup alpine:3.22 sh -c "find /data -mindepth 1 -delete && tar xzf /backup/nibleaf-storage-$STAMP.tar.gz -C /data"
```

### Start v0.1.2

```bash
docker compose up -d
NIBLEAF_VERSION="$STAGE" queues resume
NIBLEAF_VERSION="$STAGE" queues status
```

**Expected:** `NIBLEAF_VERSION` is back to `v0.1.2`, services are healthy, and both
queues show `"paused":false`. Then repeat the product test from step 13. Keep
`nibleaf_failed_upgrade` until you have finished investigating.

## After the upgrade

v0.2.0 does not turn these on by itself.

- **Integrations.** Treat `INTEGRATION_CREDENTIAL_ENCRYPTION_KEY` like a database
  password and back it up with `.env`. Do not change it once integrations are in use:
  saved credentials become unreadable. To replace it, follow the
  [rotation procedure](/reference/integrations-engine). Do not reuse the Git key.
- **MCP.** The endpoint stays off until you set `MCP_ENABLED=true`. Read the
  [MCP guide](/self-hosting/mcp) before you enable it.
- **Search and AI.** `docker-compose.prod.yml` does not include Qdrant, and AI needs a
  provider key that you supply. `OPENROUTER_API_KEY` reaches the services through
  the optional `docker-compose.search.yml` overlay, so AI writing assist and hybrid
  search both need it. The overlay is in the repository, not in the release assets.
  Follow [hybrid search and grounded answers](/self-hosting/search-ai).
- **Analytics.** `docker-compose.prod.yml` does not include ClickHouse, and analytics
  stays in its existing mode until you follow the
  [ClickHouse guide](/self-hosting/clickhouse-analytics).
- **Clean up.** Once you are sure you will not roll back, remove the staged image with
  `docker image rm "ghcr.io/lord007tn/nibleaf:$STAGE"`, and move your backups to
  long-term storage.
