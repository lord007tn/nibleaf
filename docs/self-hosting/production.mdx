A green container is not a production launch. Prove the complete path from DNS
and TLS through the application, storage, email, publishing, search, backups,
and restore.

## Verify DNS and TLS

Test every intended origin independently:

- dashboard `APP_URL`;
- storage `STORAGE_PUBLIC_ENDPOINT`;
- optional admin origin;
- one project under `SITE_BASE_DOMAIN`;
- the custom-domain CNAME target;
- one real external custom domain.

A wildcard project domain needs wildcard DNS and a certificate covering
`*.<base-domain>`. Let's Encrypt wildcard certificates require a DNS challenge.
For custom domains, preserve the validated original `Host` header through the
ingress because Nibleaf uses it to select the project.

## Verify service health

Run from the deployment directory. In a guided-installer directory, omit
`-f docker-compose.prod.yml`:

```bash
docker compose -f docker-compose.prod.yml ps
docker compose -f docker-compose.prod.yml logs migrate
docker compose -f docker-compose.prod.yml logs --tail=200 server worker app
```

The server and worker expose internal `/health` responses; the app health check
requests `/sign-in`. Keep those checks on the internal network or loopback. The
worker returns 503 while email delivery is required and no provider is configured.
Then test actual behavior: create an account and sign in with an emailed code,
upload an image, publish a two-page project, search the second page, and request a
missing page.

For enabled optional workflows, also create and download one [export](/product/exports),
exercise a [redirect](/redirects), complete one [Git push and preview](/git-authoring),
and prove both authorized and unauthorized [private reader access](/private-reader-access).

On v0.2.0 or later, additionally verify complete/partial/unavailable usage states,
one add-on consent cycle, and, for each one you enable, search diagnostics without
content leakage, one non-production integration lifecycle, and one least-privilege
MCP key from creation through revocation. Search needs the
[optional Qdrant overlay](/self-hosting/search-ai), integrations need
`INTEGRATION_CREDENTIAL_ENCRYPTION_KEY`, and [MCP](/self-hosting/mcp) is off by
default.

## Verify security boundaries

Confirm that:

- internal ports are unreachable from the internet;
- worker operations require credentials;
- authentication and OAuth redirects use the public origin;
- object-storage credentials are limited to the intended bucket;
- public HTML carries the expected security headers and request-specific CSP;
- admin and token-bearing auth pages are not indexable;
- sign-up policy matches the intended audience;
- private reader, audience, and JWT rules deny an ungranted page and search result;
- Git provider credentials use the documented minimum repository scopes;
- backups use separate access control from the live service.

Do not publish secrets, customer content, access tokens, or full environment
files in logs, screenshots, issues, or support discussions.

## Monitor the user path

Monitor container health, failed publish and export jobs, queue depth, Postgres
disk usage, object-storage usage, backup age, certificate expiry, 5xx responses,
and mail delivery. Add an external check for the canonical homepage and one deep
published page, not only the app port.

Set alerts before launch and record who responds to them.

## Record the launch gate

Launch only when a durable record contains the image tag and digest, migration
result, DNS and TLS evidence, public 200/redirect/404 checks, upload and search
evidence, last backup identifiers, isolated restore result, and the owner of
alerts and upgrades.

Complete [backup and restore](/self-hosting/backups-upgrades) before the first
production content publish.


## Analytics capacity and recovery

Keep analytics health independent from core readiness. The source quickstart/Coolify ClickHouse budget
is a starting point for small hosts; measure disk headroom before enabling ingestion.
Review [analytics operations](/self-hosting/clickhouse-analytics) and perform the
[isolated analytics restore drill](/self-hosting/backups-upgrades) before upgrades.
Non-Coolify inline Compose configs require Docker Compose 2.23.1 or newer.
The Coolify file instead uses its documented bind-mount `content:` extension to
create the ClickHouse XML file. Plain `docker compose config` rejects this
Coolify-only extension; deploy that file through Coolify.

## Check current-source AI and MCP separately

The pinned v0.2.1 Compose file has no ClickHouse service. The current-source
analytics, workspace provider, chat and MCP OAuth guides need v0.2.1 or a later
image, migrations and explicit environment wiring. An environment example does
not prove the released Compose file passes a setting.

For features you deploy, verify the chosen provider and READY publication index,
one English and one Arabic chat answer with working citations, a refusal, stop
and retry, and a budget-limited request. Confirm transcript capture matches the
site setting and visitor consent, and that unknown usage remains unknown.
Provider verification only reads model catalogs; perform a real question to
check account credit and model availability. Editor drafting still uses the
instance OpenRouter key, separately from a workspace search provider.

For MCP OAuth, check discovery on the HTTPS dashboard origin, connect one
least-privilege app, and verify disconnect stops the next request. For MCP
writes, preview a fictional project with another writer’s pending draft and
confirm the preview includes the whole project before publishing.

## Next-release packaging and source CI

`release/self-host.json` and `release/published/` describe the published v0.2.1
assets. `docker-compose.prod.yml` and `scripts/install.sh` now prepare the next
release; they do not change existing downloads. Do not replace a released
installation with these templates as an upgrade shortcut.

The next template includes optional ClickHouse with a 1536 MiB / 2 CPU budget, persistent
data, logs and backups, and an `analytics-tools` migration profile. Analytics
remain disabled by default. Set `COMPOSE_PROFILES=analytics` and choose an
`ANALYTICS_MODE` from the rollout guide to enable it. Set `CLICKHOUSE_PASSWORD` before rendering this
template (the next installer generates it) and keep `INTERNAL_API_SECRET` the
same on app, API and worker. Reader and writer credentials can be set separately;
provision the corresponding ClickHouse users and grants as described in
[analytics operations](/self-hosting/clickhouse-analytics). The template also
forwards every documented `EXPORT_*` setting and both MCP write/publish limits.

For an existing v0.2.1 installation needing those limits before the next release,
use a separate `compose.limits.yml` override. Set the required `EXPORT_*`,
`MCP_WRITE_RATE_LIMIT_PER_MIN` and `MCP_PUBLISH_RATE_LIMIT_PER_HOUR` mappings on
`server` and `worker`, then use the same ordered file list for every command:

```bash
docker compose -f docker-compose.yml -f compose.limits.yml config
docker compose -f docker-compose.yml -f compose.limits.yml up -d server worker
```

Review the effective environment privately; it contains secrets. Rehearse with
fictional data and verify the actual limits before production. The published
Compose comments about skipping private proxy hops are stale: count every address
after the client, private addresses included. Use the
[proxy troubleshooting table](/self-hosting/troubleshooting#readers-see-too-many-requests).

Manual image publication/deployment requires successful `push` runs of
`ci.yml`, `codeql.yml`, and `gitleaks.yml` for the exact source SHA. Missing,
pending, cancelled, failed or unreadable results stop the gate. There is no bypass.
Pull-request merge runs cannot qualify a different published source tree. The
manual workflow builds an OCI archive first, rechecks CI immediately before
copying that archive to the registry, then rechecks again before deployment.
The named required job must pass too; a successful workflow wrapper is insufficient.
Docker builds remain manual-only. A read-only receipt can be obtained with:

```bash
SOURCE_SHA=$(git rev-parse HEAD) GITHUB_REPOSITORY=lord007tn/nibleaf GH_TOKEN="$(gh auth token)" node scripts/check-source-ci.mjs
```

At the next release preparation, set the new version in the production template,
copy the reviewed templates into `release/published/`, regenerate both hashes and
the verified README command together, and run `pnpm self-host:check` and
`pnpm release:check`. Publish fresh assets under a new tag; never replace v0.2.1.
`pnpm self-host:smoke` boots these templates with fictional credentials in the
isolated `nibleaf-selfhost` project, checks app/worker/analytics health and runs
the analytics migrator while the worker runs, then removes its own stack.
It uses the compatible v0.2.1 image; publishing new assets remains a release action.

## Marketing HTML and CDN caching

Allowlisted marketing pages on `nibleaf.com` now use hash-based script CSP and
`public, max-age=60, s-maxage=300` for GET/HEAD requests without any Cookie,
Authorization or query string. They contain no nonce metadata. Dashboard,
authentication, reader, unknown and credential-bearing routes keep request
nonces and `private, no-store`. Errors and responses setting cookies are private.

Marketing rendering completes Suspense before emitting HTML, normalizes router
timestamps before dehydration, and computes hashes after the manifest rewrite.
The footer year is fixed at build time. Set `MARKETING_GITHUB_STARS` to a verified
nonnegative integer when building to display a fixed star count; the default 0
is the unavailable-count fallback. Counts and year refresh on the next build.
For a Docker source build, pass `--build-arg MARKETING_GITHUB_STARS=<verified-count>`.
The built-app CI guard compares human/bot HTML and checks every inline hash on
English and Arabic pages after every framework upgrade.

The owner accepted these trade-offs: GTM custom-HTML inline scripts are blocked
unless covered by the policy, while allowed GTM script loading remains available;
CDN hits bypass origin crawler analytics; public values may be stale in caches.

Before enabling HTML caching at the CDN, install a bypass rule with precedence
over the marketing cache rule for any Cookie or Authorization header or query
string. Match only `nibleaf.com`, the allowlisted marketing paths and GET/HEAD;
never cache `/app`, `/sites`, authentication or unknown routes. Include the host
and negotiated Accept representation in the cache key, preserve `Vary: Accept`,
and honor origin Cache-Control and Set-Cookie. `Vary: Cookie` alone is insufficient.
Keep the CDN disabled until these rules are verified. This source change does
not claim a live CDN rollout. On deployment, purge cached marketing HTML or retain
the previous build's hashed assets through the cache lifetime.

## CLI agent-resource checks

`inspect` rejects empty or HTML/login `llms.txt`, including disguised HTML, while
accepting English and Arabic UTF-8 text. OpenAPI requires JSON, version 3.0.x or
3.1.x, nonempty `info.title` and `info.version`, and a `paths` object (which may be
empty). This is a minimum document-shape check, not full OpenAPI validation.
Failures identify the resource and corrective action; Markdown, `Vary: Accept`
and real-404 checks still apply.
