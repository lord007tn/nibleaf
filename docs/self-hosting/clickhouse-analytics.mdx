Postgres owns accounts, projects and publishing. ClickHouse stores analytics.
**Analytics unavailable means your documentation site is fine.** Unknown metrics
must not be interpreted as zero. The reader never connects to ClickHouse.

## Choose a mode

| Mode | When to use it |
| --- | --- |
| `disabled` | Keep relational analytics; no ClickHouse ingestion or boot migrations. |
| `dual_write` | Write both stores while validating and backfilling ClickHouse. Legacy dashboards use Postgres; insights are not configured. |
| `shadow_read` | Compare legacy reads while validating ClickHouse. The new insights dashboard reads ClickHouse. |
| `clickhouse` | After reconciliation, use ClickHouse analytics and stop relational analytics writes. |

Back up both stores before advancing. Run `pnpm analytics:backfill -- --project=<id>`
and `pnpm analytics:reconcile -- --project=<id>`, then observe a full reporting
window. Keep relational history through the rollback window. Returning to
`dual_write` cannot restore relational events missed in ClickHouse-only mode.

## Migrations and health

The worker starts migrations in the background when analytics is enabled and
`CLICKHOUSE_MIGRATE_ON_BOOT=true` (default). It creates the database if missing,
applies pending versions and reapplies retention TTLs. Retry delay grows from
one second to a maximum of 60 seconds. Neither migration nor ClickHouse health
gates core startup. All workers and the migration CLI must share the same
Postgres database: a transaction-scoped PostgreSQL advisory lock serializes
migration work for the ClickHouse database name. Lock contention retries without
running DDL. The lock transaction has a one-hour ceiling; investigate hung work
well before that ceiling and never launch an overlapping manual migration.

For a dedicated migration identity, disable boot migrations and run:

```bash
docker compose --profile analytics-tools run --rm analytics-migrate
# Or from a source checkout with POSTGRES_URL and ClickHouse writer credentials:
pnpm --filter @nibleaf/clickhouse migrate
```

The command reports failure if another process holds the lock; rerun after it
finishes. Server and worker `/health` include this independent field:

```json
{"analytics":{"configured":true,"latencyMs":4,"status":"ok"}}
```

`disabled` means off; `migrating` means this process is applying the schema;
`schema_outdated` means at least one migration version is missing (including an
uninitialized database); `unavailable` means connection, credentials or schema
probing failed; `ok` means every code migration is recorded. The API independently
probes the database, so it can report `schema_outdated` while a worker migrates.
The optional schema probe has a 750 ms deadline so an outage stays inside the
container healthcheck timeout. Core readiness and its HTTP status continue to
depend on core services only.

## Credentials and privacy

Generate an independent `ANALYTICS_HASH_SALT` with `openssl rand -hex 32`. Preserve
existing salts and keys; changing a salt splits historical visit identities.
Sessions use salted hashes, with a per-tab session identifier. Consent states
are `granted`, `denied`, `unknown`, and `not_required`; sensitive search text is
eligible only for `granted` or `not_required`.

Public search terms require a public site and the project setting
`analytics.storePublicSearchTerms=true`. Private sites never store raw terms.
Terms are normalized (NFKC, lowercase, trimmed, collapsed whitespace), and emails,
URLs and digit runs of six or more characters are redacted before hashing and
storage. Text appears only after at least **2 distinct visits** searched the term;
others contribute to hidden-term totals. Sensitive text has its own short TTL.
No document bodies, prompts or answers belong in product analytics events.

Compose bootstraps a writer identity; it does not provision a separate reader.
Create a reader with SELECT on the analytics database (including migration
versions and the sensitive table needed for eligible terms), then set
`CLICKHOUSE_READER_USERNAME` and `CLICKHOUSE_READER_PASSWORD`. Protect those
credentials: SQL privileges are database-wide; tenant scoping is enforced by
Nibleaf queries. The writer needs INSERT, CREATE and ALTER for migrations, TTLs,
rollups and project erasure; database creation may require an operator grant.
Use a dedicated operator identity for CLI migrations if runtime DDL is prohibited.
Never reuse reader credentials for writes. Keep passwords in deployment secrets.

Deleting a project erases its raw, sensitive and rollup analytics with a deletion
fence. Verify ClickHouse mutations finish before closing an erasure request.
Restoring an older backup can resurrect erased records: replay deletions before
connecting restored data to the application.

## Retention and disk headroom

| Variable | Default days | Allowed range |
| --- | --- | --- |
| `CLICKHOUSE_RAW_RETENTION_DAYS` | 180 | 7?730 |
| `CLICKHOUSE_CRAWLER_RETENTION_DAYS` | 90 | 7?730 |
| `CLICKHOUSE_ROLLUP_RETENTION_DAYS` | 730 | 30?3650 |
| `CLICKHOUSE_SENSITIVE_RETENTION_DAYS` | 30 | 1?90 |

Every migration run reapplies TTLs with `materialize_ttl_after_modify=0`.
Changes affect subsequent merges without an immediate rewrite; deletion is
asynchronous. Shortening retention permanently removes older history.

Bundled Compose limits ClickHouse to 1.5 GiB container memory, with a 1 GiB server
budget and 128 MiB mark cache, and rotates warning logs. Noisy system log tables
are disabled for new writes; existing system tables still occupy disk and need
operator review. These are starting limits, not a capacity guarantee. Monitor
free bytes, queue age, failed jobs, parts, merges and mutations. Never delete
files under the ClickHouse data volume to free space. See
[backups](/self-hosting/backups-upgrades) and [troubleshooting](/self-hosting/troubleshooting).
