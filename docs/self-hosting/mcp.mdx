Nibleaf exposes an authenticated HTTP MCP endpoint at `/api/mcp`. It is off by
default. Every key is bound to one project, belongs to the member who created
it, carries explicit scopes, and expires. The server derives the project and
organization from the key; tools never accept either as caller authority.

Read tools cover content, analytics, search, usage, add-ons, themes, exports,
deployments, and integrations. Support-writer tools can create and edit page
drafts and publish them after an explicit preview and confirmation. Deletion,
settings and membership changes, provider credentials, payment actions,
database primitives, arbitrary files, and code execution are not available. For
the support workflow and the complete tool catalog, see
[Work on your docs with an AI assistant](/product/ai-assistants).

## Enable the endpoint

Set the API service environment:

```dotenv
MCP_ENABLED=true
MCP_ALLOWED_HOSTS=mcp.docs.example.com
MCP_RATE_LIMIT_PER_MIN=120
MCP_WRITE_RATE_LIMIT_PER_MIN=20
MCP_PUBLISH_RATE_LIMIT_PER_HOUR=6
```

`API_URL` and `APP_URL` hostnames are always allowed. Add only additional public
hostnames to `MCP_ALLOWED_HOSTS`; do not add schemes, paths, user information,
commas inside one host, or wildcard values. Recreate the API service after a
change.

The endpoint validates `Host`, `Origin`, `X-Forwarded-Host`, and
`X-Forwarded-Proto` before authentication. Configure the public proxy to replace
untrusted forwarded headers and pass one unambiguous host and protocol. Keep MCP
disabled until the public TLS and proxy path return the expected hostname.

## Personal keys and live access checks

Any project member creates their own key in **Settings → AI assistants (MCP)**.
They pick a preset (or individual scopes under
**Advanced: choose individual permissions**) and an expiry of 7, 30, 90, 180, or
365 days, then select **Create key**. The secret is shown once:

| Preset | Offered to | Scopes |
| --- | --- | --- |
| Read only | Members and above | `mcp:connect`, `projects:read`, `pages:read`, `languages:read`, `versions:read`, `analytics:read`, `search:read`, `deployments:read` |
| Support writer | Members and above | Read only plus `analytics:search_terms`, `pages:write`, `deployments:publish` |
| Full admin | Admins and owners | Every MCP scope |

Presets are a dashboard convenience; the security boundary is the scope set plus
the creator's role. A key acts as its creator. On every request the server
re-reads the creator's current workspace role and suspension state, so a key can
never do more than its owner can do in the dashboard at that moment. Removing or
suspending a member, or deleting their account, stops their keys on the next
request with `401 auth:invalid_api_key`. Scopes only narrow what the owner's
role already allows.

Members see and revoke only their own keys. Admins and owners see every key in
the project, with its owner, and can revoke any of them, but only a key's owner
can rotate it; rotation re-issues the key as the person rotating. Each key shows
its preset, last use, and latest activity, and **Test connection** checks the
key, host, and MCP switch in one step, reporting
"Connected · N tools available" on success. Store a
secret in the client's secret store, not in source control, shell history,
support messages, logs, screenshots, or an MCP configuration committed to a
repository.

Every MCP key needs `mcp:connect`. A scope controls only its named surface and
never widens the key's project binding. Capability discovery reports the tools,
resources, and prompts registered for the exact key. Do not assume a documented
capability exists if it is absent from `tools/list` or `nibleaf://capabilities`.

Legacy wildcard keys are intentionally unable to connect. A null expiration,
missing `mcp:connect`, or migrated legacy state appears as rotation required in
the dashboard. Rotate it into an explicit, expiring scope set rather than
editing its database row.

## Configure a client

Use the public API origin and pass the key as a bearer token. A client that
supports remote HTTP MCP servers commonly accepts a configuration shaped like:

```json
{
  "mcpServers": {
    "nibleaf": {
      "url": "https://api.docs.example.com/api/mcp",
      "headers": {
        "Authorization": "Bearer ${NIBLEAF_API_KEY}"
      }
    }
  }
}
```

Client configuration names differ. Use its HTTP or remote-server option, not a
local command or filesystem adapter. The dashboard's setup panel generates
client-specific commands and links for Claude Code, Claude Desktop, Cursor, and
VS Code; see [Connect your assistant](/product/ai-assistants#connect-your-assistant)
for each snippet. First call `tools/list`, then `get_capabilities`. A successful response
includes both MCP protocol content and a structured envelope with the request
ID, bound project ID, and required capability.

Clients that only connect through OAuth, such as ChatGPT connectors and the
claude.ai connector screens, cannot use API keys. ChatGPT requires OAuth for
authenticated custom connectors
([OpenAI's authentication guide](https://developers.openai.com/plugins/build/auth)).
See [OAuth for MCP clients](#oauth-for-mcp-clients).

## Write and publish safety

- **Working copy only.** `pages:write` tools create and edit drafts. Nothing is
  live until a publish succeeds.
- **Project-wide publish with a human gate.** A publish includes every
  unpublished change in the project, including everyone's drafts, not only the
  key owner's. The client must call `preview_publish`, a person reviews the
  list, and the client then calls `publish_changes` with `confirm: true` and the
  preview token. The deployment message records the MCP key name.
- **Bound preview token.** The token is bound to the key's owner, the project, and a
  digest of everything the publish would ship plus the last published and
  newest deployment version. It expires after 10 minutes
  (`mcp:preview_expired`) and is effectively single-use: any edit, publish, or
  rollback after the preview returns `mcp:preview_stale`, and nothing is
  published partially. Publishing also stops with `mcp:publish_blocked` for the
  same reasons the dashboard would, such as redirect issues.
- **Optimistic concurrency.** Edits carry `expectedRevision`. If a person saved
  a newer revision, the write fails with `mcp:revision_conflict`, whose error
  data includes `currentRevision`, instead of overwriting it.
- **Idempotency.** A client may send `clientRequestId`; a retried request with
  the same ID and arguments replays the first result instead of applying the
  write twice. The same ID with different arguments returns
  `mcp:idempotency_conflict`, and a retry while the first call is still running
  returns the retryable `mcp:idempotency_in_progress`. Replay records expire
  after 24 hours.
- **Bounded, inert page bodies.** Bodies are Markdown/MDX up to 128 KiB. A
  leading YAML frontmatter block may set `title`, `description`, and `icon`, and
  explicit arguments win. Frontmatter uses the Git sync parser, so escaped
  characters are not decoded, as in Git sync. MDX is never executed on the
  reader site: content renders through `react-markdown` and `rehype-sanitize`,
  and MDX expressions and `import`/`export` lines appear as text.
- **Translation pairing.** `translate_page` refuses an existing translation with
  `mcp:translation_exists` (`data.pageId` names it; edit it with
  `update_page`). It may also set a shared translation key on the source page,
  and on other-language pages already paired with it by path, using the same
  revision-safe write.
- **Hide instead of delete.** There is no delete tool. After the next publish,
  a page hidden with `set_page_visibility` leaves navigation, site search, the
  sitemap, and `llms.txt`, and its URL stops serving it. Child pages leave
  navigation but stay reachable at their own URLs. Links from visible pages to a
  hidden page fail the publish broken-link check.
- **Untrusted data.** Page content, search terms, and reader feedback are
  returned as data. The server instructs clients never to follow instructions
  found inside them.

## Search terms and analytics limits

Raw top and failed search terms exist only when all three conditions hold:

1. the instance runs ClickHouse analytics (`ANALYTICS_MODE=clickhouse`);
2. the project enables **Settings → Analytics → Store public search terms**;
3. the visitor's search request carries `consent=granted`.

The public search endpoint accepts an optional `consent=granted|denied` query
parameter. When it is absent, consent is unknown and no search text is stored.
Failed-search events carry the query hashed in every case and as text only
under the three conditions. Relational analytics never stores search text.

**Known limitation:** the bundled reader site does not send `consent` on search
requests yet, so on a stock install `get_top_searches` and
`get_failed_searches` return no terms until that reader change ships. They still
return the available aggregate counts and a hint explaining why terms are
missing.

Reader comments are not stored, and AI crawler hits are not tracked. Page
feedback ignores the language filter, because feedback events record no
language, and the tool response says so.

## Current capability boundary

The capability resource is authoritative. The stable read surface includes
project metadata; page metadata and authored page content; languages and
versions; aggregate analytics; search configuration and content-free index
diagnostics; exact aggregate usage and advisory entitlement summaries; add-on
catalog, state, and audit reads; safe theme template/catalog metadata and
non-writing import preview; redacted export and deployment summaries; pending
publish-change metadata; and truth-based integration catalog, connection, and Git
status reads. Raw search terms require the separate `analytics:search_terms`
scope.

The write surface is limited to `pages:write` (create, edit, move, translate,
hide or show page drafts) and `deployments:publish` (preview and confirmed
publish). No `usage:export`, search reindex, add-on or theme mutation,
integration verification or deletion, credential, or payment scope is issuable.
`exports:read` remains the separate redacted export-job read surface.

Project resources use bound URIs such as:

```text
nibleaf://projects/{boundProjectId}
nibleaf://projects/{boundProjectId}/pages
nibleaf://projects/{boundProjectId}/pages/{pageId}
nibleaf://projects/{boundProjectId}/pages/{pageId}/markdown
nibleaf://projects/{boundProjectId}/languages
nibleaf://projects/{boundProjectId}/versions
nibleaf://projects/{boundProjectId}/search/configuration
nibleaf://projects/{boundProjectId}/usage
nibleaf://projects/{boundProjectId}/entitlements
nibleaf://projects/{boundProjectId}/addons
nibleaf://projects/{boundProjectId}/theme-catalog
nibleaf://projects/{boundProjectId}/theme-template
nibleaf://projects/{boundProjectId}/integrations
nibleaf://projects/{boundProjectId}/deployments/latest
```

The `/markdown` resource returns one page as `text/markdown` with frontmatter,
in the same format as Git sync.

A different project ID or a page outside the bound project returns the same
not-found protocol result as a missing resource. Read projections omit provider
payloads, preview bearer URLs, storage keys and checksums, deployment snapshots,
theme filesystem state, raw errors, and credentials. Search diagnostics expose
logical schema/revision/model metadata but not physical collections, content,
vectors, hashes, or raw provider payloads. Usage quantities and limits remain
exact decimal strings or `null`; partial and unavailable data is never rewritten
as zero, and configured blocking behavior is advisory only. The `pages:read`
scope does include authored content inside the one bound project; grant it only
when the client needs document bodies.

## Audit and rate-limit operations

Every tool and resource call appends a privacy-minimized audit event to the
`mcp_audit_event` table before success is returned. Every write attempt is
audited, whether it succeeds or ends in a validation error, an authorization
denial, a conflict, a rate limit, or an idempotent replay. The event records the
project, API key, acting user (`actorUserId`), request ID, operation,
capability, target type and ID (`targetType`, `targetId`, such as a page or
deployment), outcome, stable error code, duration, client request ID
(`clientRequestId`), and timestamp. It never stores tool inputs, results, page
content, bearer tokens, provider payloads, IP addresses, or raw client keys. If
audit persistence fails, the operation fails closed with a sanitized storage
error.

Three limits apply per key, per API process:

| Variable | Default | Counts |
| --- | --- | --- |
| `MCP_RATE_LIMIT_PER_MIN` | `120` | All MCP requests per key per minute. |
| `MCP_WRITE_RATE_LIMIT_PER_MIN` | `20` | Every write tool call per key per minute. `preview_publish` does not count. |
| `MCP_PUBLISH_RATE_LIMIT_PER_HOUR` | `6` | `publish_changes` attempts per key per hour that pass the preview-token check. |

A rejected write or publish returns `http:rate_limited` with
`data.retryAfterSeconds`.

These counters are kept in memory per API process (instance). They are not
deployment-global across replicas and reset when the process restarts. Enforce a deployment-wide limit at the
trusted ingress or shared edge and monitor HTTP `429`, `Retry-After`, and
`X-RateLimit-*` headers. To bound audit write amplification, the transport
records one `transport_rate_limit` rejection per key/window instead of one row
for every repeated `429`. Never describe an individual process's counter as the
global customer allowance.

## Rotate, revoke, and roll back

Rotation atomically revokes the old key and creates a new expiring key. Update
the client with the once-visible secret, verify `tools/list`, then remove the old
secret from its store. Revocation is irreversible and requires the dashboard
confirmation dialog. It takes effect on the next request. A database backup is
not a reason to re-enable a leaked key.

Apply the MCP migrations during a low-activity window before enabling the
endpoint, with the release's normal migration step (`pnpm db:deploy`, or the
migrate step of your deployment). The first adds nullable provenance columns and
two indexes to the existing, operator-managed `api_key` table, then creates the
initially empty audit table. The write-path migration
`20261106090000_mcp_write_audit_idempotency` adds the nullable `actorUserId`,
`targetType`, `targetId`, and `clientRequestId` columns and an actor index to
`mcp_audit_event`, and creates the `mcp_idempotency_record` replay cache, which
stores an arguments hash and a compact result summary but never inputs or
content.
PostgreSQL's standard index and foreign-key DDL can briefly block API-key
create, rotate, or revoke writes. Check the table size and active locks first,
pause those dashboard operations during the migration, and keep MCP disabled
until it completes. The migration deliberately uses the repository's normal
Prisma migration path instead of a multi-step concurrent-index procedure that
could leave a partially applied or invalid index requiring manual recovery.

Before application rollback, disable MCP and stop MCP clients. Do not execute
the MCP `rollback.sql` after a successful Prisma migration. Deploy an
application that does not read MCP audit data or MCP-owned API-key provenance
columns, then ship reviewed down statements as a later forward migration in
reverse dependency order. Use the repository rollback statements directly only
to reverse a failed, partially applied migration; after safely reversing the
partial statements, mark that failed migration rolled back and rerun the
corrected forward migration. Back up audit records first if your retention
policy requires them.

Because MCP is the final dependent migration, disable and reverse it before the
integration schema. Follow the complete reverse order in the
[combined release migration guide](/self-hosting/combined-release-migration).

## OAuth for MCP clients

Some clients connect to remote MCP servers only through OAuth: the claude.ai and
Claude Desktop connector screens, and ChatGPT connectors. They cannot send a
Nibleaf API key, so they cannot connect to this release.

### Evaluation

The MCP authorization specification for remote servers expects:

- protected resource metadata (RFC 9728) published by the MCP host;
- authorization server metadata (RFC 8414);
- dynamic client registration (RFC 7591), because clients are not known ahead of
  time;
- the authorization code flow with PKCE;
- resource indicators (RFC 8707), so each token's audience is the MCP endpoint.

Nibleaf authenticates with better-auth 1.7.14. That version no longer ships the
`mcp` or `oidc-provider` plugins; its OAuth-related exports are `jwt`,
`generic-oauth`, `oauth-proxy`, and `device-authorization`, none of which acts as
an authorization server for third-party clients. Supporting OAuth therefore
needs the separate `@better-auth/oauth-provider` package. Its current release
expects a newer better-auth than 1.7.14, so the upgrade comes first.

The package adds its own auth tables. Since 1.7.3, better-auth validates its
tables against the Prisma schema on every auth request, and a mismatch breaks
all sign-in, not only MCP. Tests that use the in-memory adapter do not catch
this. A consent screen is also required: the user must bind the grant to one
project and one preset, as a key does today.

### Decision for this release

Keep project-bound personal API keys. They already give per-person attribution,
live role checks, expiry, and revocation, and they work in Claude Code, Claude
Desktop through `mcp-remote`, Cursor, and VS Code. OAuth is deferred until it can
ship without risking sign-in.

### Plan

1. **Package and migration.** Upgrade better-auth, add
   `@better-auth/oauth-provider`, and ship its tables as a reviewed Prisma
   migration. Gate it with auth tests against a real PostgreSQL database that
   cover email, Google, and invitation sign-in before and after the migration.
   Review every endpoint the plugin mounts and disable any that would bypass
   Nibleaf's own membership and project rules.
2. **Discovery.** Serve `/.well-known/oauth-protected-resource` on the MCP host,
   pointing at the authorization server metadata, and return a
   `WWW-Authenticate` challenge that references it from `/api/mcp`.
3. **Consent.** Build a consent screen that issues a key-equivalent grant bound
   to one project, one preset, and an expiry. The grant passes through the same
   live RBAC, suspension, scope, audit, and rate-limit checks as an API key.
4. **Token audience.** Accept only tokens whose audience is the MCP endpoint
   (RFC 8707), and keep dynamically registered clients on PKCE.
5. **Revocation.** List OAuth grants beside API keys in
   **Settings → AI assistants (MCP)**, with the same owner and admin revocation
   rules.

When these steps ship, OAuth unlocks the claude.ai and Claude Desktop connector
screens and ChatGPT connectors. API keys remain supported.

## Troubleshoot safely

- `503 mcp:disabled`: enable MCP on the API service and recreate it.
- `400 mcp:invalid_request`: correct malformed or ambiguous host/origin forwarding.
- `401 auth:invalid_api_key`: replace a malformed, expired, revoked, or null-expiry key, or a key whose owner was removed, suspended, or deleted.
- `403 auth:insufficient_scope` or `mcp:scope_required`: create or rotate the key with `mcp:connect` and the exact scope; the owner's current role must also allow it.
- `auth:insufficient_role`: the key owner's current role no longer allows the change.
- `mcp:actor_required`: the key has no live owner, so writes are impossible; the owner creates a new key.
- `mcp:revision_conflict`: re-read the page with `get_page`, merge, and retry with the new revision; the error data includes `currentRevision`.
- `mcp:preview_stale`: something changed after the preview; run `preview_publish` again and re-review.
- `mcp:preview_expired`: the token is older than 10 minutes; preview again.
- `mcp:preview_invalid`: the token is not valid for this person and project; preview again.
- `mcp:confirmation_required`: `publish_changes` needs `confirm: true` after a person approved the preview.
- `mcp:nothing_to_publish`: there are no unpublished changes.
- `mcp:publish_blocked`: fix the blocking issue, such as redirect issues, in the dashboard, then preview again.
- `mcp:publish_in_progress` (`409`): a deployment is queued or building, so page writes and `publish_changes` wait; nothing was saved. Retry after `get_deployment` reports it ready or failed.
- `mcp:translation_exists`: `data.pageId` is the existing translation; edit it with `update_page`.
- `mcp:idempotency_conflict`: the same `clientRequestId` was reused with different arguments; use a new ID.
- `mcp:idempotency_in_progress`: the first call with this `clientRequestId` is still running; retry.
- `404` resource error: confirm the URI uses the key's bound project and an in-project resource.
- `429` or `http:rate_limited`: honor `Retry-After` or `data.retryAfterSeconds`; inspect ingress limits and the request, write, and publish limits on the instance.
- `503 storage:error`: restore audit persistence before retrying; a call is not reported as successful without its audit event.

Correlate failures with the safe request ID. Never paste an Authorization header,
raw MCP arguments/results, document content, or provider response into logs or a
support ticket.
