Six capability pull requests are integrated in Nibleaf source on `main`. They
form one coherent control plane for search, usage, add-ons, themes,
integrations, and agent access. This is source availability, not deployment
evidence: the committed self-host manifest still points to v0.1.2, and no Cloud
or self-host deployment is performed by these documentation changes.

## Search and grounded answers

The search domain supports tenant-, deployment-, language-, version-, and
reader-authorization-scoped retrieval. Project settings expose result count,
language/version filters, and optional grounded answers. Diagnostics show
health, counts, stable issue codes, and bounded identifiers; they never return
document content or vectors.

Hybrid operation is not a universal quality claim. Keep `SEARCH_RUNTIME=shadow`
until real acceptance queries and provider evidence support a cutover. The
immediate retrieval rollback remains `legacy`. Unsupported grounded answers are
withheld rather than invented. See [search and AI operations](/self-hosting/search-ai).

## Usage and entitlement truth

Usage facts use provider-neutral meters and exact integer quantities. Postgres
owns plans, assignments, entitlements, checkpoints, and bounded low-volume
receipts; optional ClickHouse stores high-volume facts and rollups. Coverage can
be complete, partial, or unavailable. Missing history is never presented as
zero, and the feature does not enable billing or payments.

Limits remain advisory in this source capability set. Export waits for pending
or late usage to reconcile, and privacy deletion covers both stores and search
erasure boundaries. See [usage metering](/self-hosting/usage-metering).

## Add-ons and consent

Project add-ons group reader engagement, privacy, and publishing helpers behind
durable state and explicit entitlements. Feedback records a bounded sentiment
event; edit and issue links require safe URL templates; consent gates optional
analytics; local publish checks validate internal links and an explicitly
preview-quality grammar linter. See [project add-ons](/product/add-ons).

## Portable documentation themes

Harbor, Manuscript, and Signal now own different reader structures rather than
acting as color presets. All three use the same Markdown/MDX contract, semantic
tokens, localization, search, metadata, and immutable publication boundary.
Theme templates are deterministic, schema-validated JSON without executable
CSS or JavaScript. Standalone Git exports separate platform, shared-content, and
customer-owned files. See [documentation themes](/product/themes).

## Integrations and MCP

The integration engine separates external provider connections from add-ons and
usage. It encrypts configurable credentials with a dedicated key, redacts
responses and audits, uses revisions and idempotency, and requires explicit
confirmation for destructive deletion. A provider listed in the catalog is not
proof that its runtime or credentials are available.

MCP exposes project-bound read adapters for capabilities, published content,
search configuration and diagnostics, aggregate usage, entitlements, add-ons,
theme catalogs/templates, integration summaries, and bounded operational
metadata. It cannot publish, reindex, export usage, accept provider credentials,
or mutate the new domains. Theme-import preview validates without writing. See
[integrations](/reference/integrations-engine) and [MCP](/self-hosting/mcp).

## Upgrade boundary

The Postgres migrations must run in timestamp order, with integrations before
MCP because integrations owns `ApiKey.expiresAt`. Optional ClickHouse migrations
and reconciliation have their own gate. Read the
[combined migration and rollback guide](/self-hosting/combined-release-migration)
before selecting a source revision or future image.

Do not replace the v0.1.2 installer, compose digest, or container reference with
these commits. A future published artifact needs its own build, security and
migration checks, exact digest, release notes, and signed-out runtime validation.
