Start from `.env.production.example` shipped with the release. This page explains
the setting groups for the current source. The pinned v0.2.1 Compose file and
its image have a separate release boundary. Never commit a populated `.env`.

The first tables use production Compose defaults unless marked otherwise. The
search, analytics, connection, and logging tables below give **schema defaults**.
An empty value is treated as unset by the env schemas. Optional means the
process can parse without it; a feature may still require it. A value in `.env`
does not reach a container unless Compose passes it in `environment` or
`env_file`. See the release wiring notes at the end before changing a setting.

### Google OAuth

Create a **Web application** OAuth client in Google Cloud, then configure:

- Authorized JavaScript origin: the exact `APP_URL`, such as `https://nibleaf.example.com`.
- Authorized redirect URI: `${APP_URL}/api/auth/callback/google`.
- `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`: the matching client credentials.

Both variables must be present and non-blank after trimming surrounding whitespace. Nibleaf hides the Google button when either value is missing, so a partially configured provider cannot send readers into a broken sign-in flow. Restart the application after changing these server-side values.

### GTM container contract

When `MARKETING_GTM_ID` is enabled, configure one Google tag in GTM with automatic pageviews disabled and its normal page initialization trigger. Then configure one GA4 Event tag triggered by the Custom Event `nibleaf_marketing_event`, with its GA event name read from the Data Layer Variable `event_name`. Nibleaf uses that stable envelope for the allowlisted names `page_view`, `sign_up`, `cta_clicked`, `free_tool_started`, `free_tool_completed`, and `free_tool_cta_clicked`, so six separate GTM Event tags are not required. Map only the documented safe event variables. Do not add variables that read form fields, account data, document content, or arbitrary DOM values into analytics. Keep consent checks enabled on both tags. Nibleaf loads the container only after acceptance, pushes one manual `page_view` for the accepted route and each later SPA navigation, and stops event delivery when consent is withdrawn.

## Operator and lifecycle settings

### Model Context Protocol

| Variable | Required | Default | Purpose |
| --- | --- | --- | --- |
| `MCP_ENABLED` | No | `false` | Enables the authenticated project-bound `/api/mcp` endpoint. Keep it disabled until proxy and key-lifecycle checks pass. |
| `MCP_ALLOWED_HOSTS` | No | Empty | Comma-separated additional public hostnames. `API_URL` and `APP_URL` hosts are already allowed. Schemes, paths, wildcard values, and ambiguous forwarded chains are rejected. |
| `MCP_RATE_LIMIT_PER_MIN` | No | `120` | Per-key MCP requests of any kind accepted by one API process per minute. Counters are in memory per process; add an ingress/shared-edge limit for deployment-wide enforcement. |
| `MCP_WRITE_RATE_LIMIT_PER_MIN` | No | `20` | Per-key write tool calls (page drafts, edits, moves, translations, visibility, and publishes) accepted by one API process per minute. `preview_publish` does not count. |
| `MCP_PUBLISH_RATE_LIMIT_PER_HOUR` | No | `6` | Per-key `publish_changes` attempts accepted by one API process per hour. Only attempts that pass the preview-token check count. |

See [secure MCP client setup and operations](/self-hosting/mcp) before enabling
the endpoint. API keys are personal: each member creates their own, admins can
revoke any but only the owner can rotate one, and secrets are displayed once. They must not be stored in
environment examples or repository configuration.

### Bidirectional Git

| Variable | Required | Default | Purpose |
| --- | --- | --- | --- |
| `GIT_CREDENTIAL_ENCRYPTION_KEY` | To enable two-way Git | None | Exactly 32 bytes encoded as base64; encrypts provider credentials and webhook secrets. |
| `GIT_WORKER_SECRET` | To enable two-way Git | None | At least 32 characters shared by API and worker for opaque callbacks. |
| `GIT_CONCURRENCY` | No | `2` | Git operations processed by one worker. |

Generate the two secrets independently. Do not rotate the encryption key in
place: existing ciphertext cannot be decrypted with a new key. Follow the
[Git authoring rotation procedure](/git-authoring). If `WORKER_QUEUES` is set,
include `git`.

## Check release wiring before applying settings

The pinned `docker-compose.prod.yml` for v0.2.1 has no ClickHouse or Qdrant
service. It does not pass analytics variables, search variables,
`AI_DRAFT_MODEL`, `MCP_WRITE_RATE_LIMIT_PER_MIN`,
`MCP_PUBLISH_RATE_LIMIT_PER_HOUR`, `WORKER_QUEUES`, export tuning, or the new
`EVLOG_*` settings. The corresponding values in `.env.production.example` are
not proof that they reach a service. A newer setting also requires an image
that implements it; adding an environment variable cannot add a feature to an
older image.

For a reviewed current-source deployment, put missing settings in a separate
Compose override. For example, this `docker-compose.operator.yml` passes two
MCP controls and a worker queue allowlist (the listed queues enable all current
workers):

```yaml
services:
  server:
    environment:
      MCP_WRITE_RATE_LIMIT_PER_MIN: ${MCP_WRITE_RATE_LIMIT_PER_MIN:-20}
      MCP_PUBLISH_RATE_LIMIT_PER_HOUR: ${MCP_PUBLISH_RATE_LIMIT_PER_HOUR:-6}
  worker:
    environment:
      WORKER_QUEUES: ${WORKER_QUEUES:-publish,search,email,analytics,export,git,erasure}
```

Include that file in every subsequent operation:

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.operator.yml config --services
docker compose -f docker-compose.prod.yml -f docker-compose.operator.yml up -d
```

In an installer directory use `docker-compose.yml` as the first file. Keep any
search or analytics overrides in the same command as well. Do not publish the
full rendered configuration; it contains secrets.

`docker-compose.search.yml` adds Qdrant and a subset of search/chat variables to
API and worker. It does not configure authentication on the Qdrant service when
you set only the client-side `QDRANT_API_KEY`. Provision the server key too before
exposing Qdrant. `SEARCH_CHAT_SUGGESTIONS_TIMEOUT_MS` and several advanced search
knobs are not passed by that overlay; add explicit environment mappings if you
change them. Its conversation token cap matches the schema default above.

Source quickstart (`docker-compose.yml`) and Coolify include ClickHouse, backup
disk configuration and the `analytics-tools` profile. Their bootstrap settings
include `CLICKHOUSE_USERNAME` / `CLICKHOUSE_PASSWORD` (quickstart fallback
`nibleaf` / `nibleaf`), or `SERVICE_PASSWORD_64_CLICKHOUSE` (required in Coolify).
These create service credentials; the app uses reader/writer variables instead.
Do not use quickstart credentials for a public deployment.

Coolify also uses `NIBLEAF_IMAGE_TAG` (fallback `latest`),
`SERVICE_USER_POSTGRES`, `SERVICE_PASSWORD_64_POSTGRES`, `POSTGRES_DB` (fallback
`nibleaf`), `SERVICE_HEX_64_NIBLEAF`, and storage fallbacks `SERVICE_USER_STORAGE`
and `SERVICE_PASSWORD_64_STORAGE`. Set an explicit image tag and keep the generated
secrets. These are Compose inputs, not app schema variables. Review that file
before moving a portable `.env` into Coolify.

After recreating services, verify their actual behavior: health, an upload,
publishing, search, and any optional feature you enabled. A parsed environment
or a passing health endpoint does not prove mail delivery, AI provider credit,
index quality, or backup recovery.
